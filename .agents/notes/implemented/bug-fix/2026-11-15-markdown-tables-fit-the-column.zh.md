# Agent Note: Markdown 表格收在正文列内

Status: implemented

[English](2026-11-15-markdown-tables-fit-the-column.md) | 中文

## 问题

一条对比式回答——例如带 `#`、问题、位置、修复 四列的审计表——渲染得比它回答的正文更宽。这是两条规则叠加的结果：渲染器让四列及以上的表格保持自然宽度，聊天 transcript 又把这些表格推出正文列、一直到页面边缘。当自然宽度超过布局实际提供的空间时，wrapper 把多余部分裁掉，最后几列在读者 hover 表格之前一直不可见；即使没有超出，表格右边缘也仍然凸出在正文列之外。在装配后的应用上以 1100px 视口播种复现：一张四列表格越出正文列 386px，其中 240px 被裁切。

## 决策

Markdown 表格永远不比它所在宿主提供的容器更宽。`MarkdownText` 的 `.tableScroll table` 使用 `width: fit-content` 并以 `max-width: 100%` 封顶：本就能放下的表格保持自然宽度，超出可用宽度的表格收进来并在其中换行，最窄到既有的 100px 可读下限。聊天 transcript 不再加宽 `md-table-wide` 表格——容器查询突破（`--dsh-table-spare`、`--dsh-table-lead` 及其负 margin、lead padding）已删除，表格与其它块一样起止于正文列的两端。

横向滚动只在换行无法解决时保留：各列最小宽度之和超过容器的表格（语料里的十四列表格、或窄视口）继续使用 wrapper 的 `overflow-x` 回退、hover 才显示的滚动条以及键盘聚焦路径。`md-table-wide` 仍是按列数静态判定的钩子，用来选择上述 wrapper 行为；它不再决定宽度。

`ChatView` 的 `.scroll` 保留 `container-type: inline-size`。它不再是任何表格的尺寸基准，但 transcript 内没有自建容器的组件（权限预设、任务行、子代理行、交付物）会让自己的无名 `@container` 规则解析到最近的容器。

## 曾考虑的替代方案

- **保留突破，只给宽度封顶。** 宽视图继续占用页面空间，但四列表格仍会单侧凸出正文列——正是本次要消除的错位。正文列是其它所有块共用的宽度。
- **恢复此前始终按自然宽度渲染。** 那正是本次缺陷：超出 wrapper 的内容要 hover 才能看到。
- **测量每张表格并提供展开弹窗。** 这是引入宽视图时已被否决的方案；对现在能原地阅读的内容而言，它只会带来逐表观察器和交互状态。

## 后果

在桌面宽度下，四到六列表格以换行收进正文列、没有横向滚动，并与周围段落对齐。多列表格让出了页面的剩余宽度，因此换行更紧、也比以前更早触发滚动回退。所有 `MarkdownText` 宿主都继承这条封顶规则——引用块、列表项、思考行、工具卡片、插件文档——因此没有任何宿主会裁掉一张单元格本可换行的表格。规则不做任何测量：表格宽度不取决于 hover、焦点或交互状态。

## 验证

[宽表 e2e](../../../../apps/web/tests/markdown-wide-table.e2e.ts) 播种填充、多列、长 token 与四列散文表格，并在 Chromium 的 1680/1100/640px 视口下钉住：散文、填充、长单元格表格无残余横向滚动，多列表格仍有，所有表格的内容都从填充表格的左边缘开始，且每张会换行的表格随正文列变窄而变高。[提交的金标](../../../../apps/web/tests/expected/markdown-wide-table/geometry.expected.md) 只记录这些关系，不记录像素。上述数字来自装配后的应用：同一张表格在修改前于 1100px 下被裁切 240px，修改后为零。
