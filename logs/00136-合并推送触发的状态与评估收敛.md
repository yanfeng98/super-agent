# 00136 — 收敛合并推送触发的唤醒与历史状态

- **日期**：2026-11-26
- **背景**：人在已结束工单的线程里明确要求「合并并推送」时，消息作为普通 follow-up 唤醒工单，删除了 `ended`，随后 `orchestrator_ticket_merge` 因 `Only an ended ticket can be merged` 被拒；同一线程上的旧 `unavailable` 决策继续在概览与触发页显示「评估超时未决定 / 可重新评估」，形成重复评估入口。

## 1. 变更

| 位置 | 变更 |
|---|---|
| `src/core/tickets.ts` | `wake()` 对带常驻合并请求的已结束工单不再 resume：消息退回 Eval，让主会话在工单仍 ended 时用合并工具处理，保留合并前提与审核记录 |
| `src/app/views/overview.ts` | `unjudged()` 不再把线程工作已收尾的 `unavailable` 决策列为系统问题；`evals` health 同步恢复 |
| `src/app/views/records.ts` | `triggerView` 对已收尾线程上的旧消息不再提供「重新评估」，dismissed 决策也不再提供 |
| `prompts/dispatch.md`、`prompts/orchestrator.md` | 明确合并、推送、回退与清理请求是宿主动作：直接调用工单工具，不 attach 到工单，避免唤醒导致合并被拒 |
| 测试 | `core-engine.spec.ts` 覆盖常驻合并请求下 follow-up 不唤醒；`runtime.spec.ts` 覆盖工单结束后 unavailable 问题自动消失；`views.spec.ts` 覆盖收尾线程旧消息不可重排 |

## 2. 判断

- 合并、推送、回退与清理是宿主对 ended 工单的动作，不是它的 worker 的新输入；把它们当 follow-up 附加会破坏 `ended` 这个合并前提。
- `unavailable` 决策只有在线程确实还没收尾时才是问题；工作落地后它是历史记录，保留审计但不再提示或提供重新评估。
