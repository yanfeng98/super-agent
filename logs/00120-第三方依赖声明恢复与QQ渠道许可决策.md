- **日期**：2026-11-23
- **背景**：内置 IM 包（`apps/web/native/dsh-im`）把 9 个运行时依赖和 2 个可选依赖带进 workspace，其中 `nodemailer` 声明 `MIT-0`、`@tencent-connect/qqbot-connector` 声明 `UNLICENSED`。`pnpm run gen-third-party-notices` 对两者硬失败，`THIRD_PARTY_NOTICES.md` 自上次上游同步的合并提交起停在旧状态——IM 的依赖一条都进不去，而单测 `scripts/gen-third-party-notices.spec.ts` 一直是 39 通过 / 1 失败。这条失败由内置 IM 功能那次提交带进来，不是上游同步造成的。

## 2. 原因与判断

- **`MIT-0` 是白名单缺口，不是法律问题**：它是 MIT 去掉署名要求的那一版，义务严格少于 MIT，所以在 `PERMISSIVE_LICENSES` 里补一个标识即可；`AND` 组合仍按「每一项都要宽松」判断，因此不会因为新增这一项而放过混入 copyleft 的表达式（测试固定了这一点）。
- **`UNLICENSED` 是真正的分发判断**：npm 元数据没有任何授权声明。生成器的政策是「非宽松运行时依赖硬失败，因为发布它是法律决定，不能让一次重新生成悄悄吸收」，唯一现成的机器可读例外是按**精确包身份**授权（Claude Agent SDK 用的是同一机制）。本仓库定位为个人研究，项目所有者据此接受这一个身份。
- **为什么不直接把分类改成宽松**：那会让清单和代码一起说谎，也会让将来任何同名或形近的包借道通过。授权在输出里以「非宽松 + 授权说明」呈现，读者能看到真实条款。
- **边界写清楚**：授权只覆盖 `@tencent-connect/qqbot-connector` 这一个身份；其他腾讯包（`qqbot-nodejs` 是 MIT、`agently-cli` 是 Apache-2.0）本来就宽松；替换 SDK、或把本仓库对外分发（发 npm 包、发二进制）时需要重新评估——换成宽松许可的 SDK，或改成由使用者自行安装都可以。
- **上游副本另有声明**：`apps/web/native/dsh-im/THIRD_PARTY_NOTICES.md` 是上游 dsh-im 自带文件，早已写明该包 `UNLICENSED` 且未复制其源码；本仓库只补根级披露，不改上游副本。
