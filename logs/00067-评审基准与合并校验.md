# 00067 — 评审基准与合并前的主干校验

- **日期**：2026-11-19
- **背景**：上一轮列出的剩余问题里，最严重的一条是正确性问题：review 用 `execution.base..HEAD`，而 `base` 只在首次启动时记录一次。worker 在工单分支上 `git merge 主干` 或 rebase 解冲突之后，主线提交会被算进工单的 review 和 diff；同时合并只比对门禁和时间戳，评审之后新增的提交仍会带着旧 check 结果被合入。
- **范围**：`src/app/review.ts`、`src/app/runtime.ts`、`tests/`、`docs/`。

## 1. 结束采集时把基准挪到分叉点

新增 `workingBase`（`src/app/review.ts`）：在工单目录跑 `git merge-base HEAD <execution.target>`，得到工单分支真正从主干分出去的提交。

`Runtime.finishTicket` 在采集 review 之前调用它：结果与记录的 base 不同时，先把 `execution.base` 写成这个分叉点，再用新 base 采集 review。这样：

- 分支 `git merge main` 之后，review 只列工单自己的提交，diff 不再混入主线改动；
- 分支 rebase 到新主干之后，base 与主干当前位置一致，也不会把主线提交算进来；
- 普通工单（base 仍是祖先）结果不变，不会多写一次；
- `execution.target` 缺失、目录不是 git 仓库或 git 失败时保持原 base，行为与之前一致。

写 base 与 `stillEnded()` 的比较使用同一个值，避免采集过程中被别的结束或恢复抢走时覆盖。

## 2. 合并前校验分支没变

`Runtime.mergeTicket` 在门禁之后、合并之前读当前 head，与 `ticket.review.head` 比较：

- 不一致（结束之后又有提交，例如后台 shell 任务收尾时提交）→ 重新采集 review、清掉旧 check，让 check 门禁在新树上重跑，然后合并；返回值带 `recaptured: true`。
- 打开 **Require review approval** 时不自动重采，直接拒绝并提示去工单页批准新的评审，因为合并的内容必须有人看过。

这样“合并的树”和“记录里的 review + check”始终是同一次采集，不会出现评审之后偷偷多合提交的情况。

## 3. 测试

- `tests/merge.spec.ts`：新增用例覆盖 head 变化时重采 + 重跑 check（`recaptured: true`），以及打开审批时拒绝重采、不调用合并。
