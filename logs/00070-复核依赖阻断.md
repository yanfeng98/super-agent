# 00070 — 复核依赖阻断

- **日期**：2026-11-19
- **背景**：按“检查修复是否正确”的要求，逐条复核 00069 的依赖阻断实现。发现两个真实问题、一个措辞问题和一个竞态，已修复。
- **范围**：`src/app/resources.ts`、`src/core/tickets.ts`、`src/core/errors.ts`、`src/client/locales.ts`、`src/app/runtime.ts`、`tests/`、`docs/003`。

## 1. worker 能读到别的工单 id（真实问题）

`ticket/<id>` 的详情加了 `blocked_by`，但那段代码没有区分主会话和 worker。worker 读自己的工单时会看到阻塞工单的 id 和标题，违反 007 写明的“Executor 的页面不出现它读不到的工单 id”和“只读自己的工单”。

修复：`blocked_by` 只在主会话的读取中返回（`ticketId` 为空时），worker 的副本不含该字段。`tests/tools.spec.ts` 增加断言：主会话能读到 `blocked_by`，同一张工单的 worker 副本没有这个属性。

## 2. 文档说 Rebase/Discard 也会被依赖拦住（不一致）

`003` 把所有“结束类动作”的门禁写成同一句，我顺手把依赖塞进了那句，于是文档声称 Merge、Rebase、Discard 三者都会被未合并的依赖拦住；实现只在 `mergeTicket` 里检查。

依赖是合并顺序，不是工作区操作的许可：blocked 工单仍然可以 rebase（保持分支新鲜），也可以丢弃（放弃）。因此修文档而不是修代码：把依赖从句子里拿出来，改成“只有 Merge 会等它阻塞的工单合并；Rebase 和 Discard 不受影响”。

## 3. 自依赖的报错文案（措辞）

`block()` 里“自己阻塞自己”复用了 `selfLink`，面板会显示“工单不能关联到它自己”。新增 `selfBlock`（“工单不能等待自己”），`block()` 改用它；中英文都有了。测试补充自依赖拒绝。

## 4. 合并重采的竞态（防御性修复）

`mergeTicket` 在分支于评审后又有提交时会重采 review 并清掉 check。原来的写入只检查“工单仍已结束且未合并”，没有比对结束时间：如果采集期间工单恢复并再次结束，旧采集会覆盖新的 review。

修复：写入前比对 `ended.at`，不一致就放弃并报“工单在采集期间发生变化，请重新合并”。这是很窄的窗口，但覆盖的是“记录与实际合并内容不符”的那类错误，值得加。

## 5. 复核后确认没问题的点

- `blockedBy` 存的是 JSON 列，加字段不需要迁移；读取没有 schema 校验会丢弃字段的问题。
- 环检测方向正确：新增 A→B 时从 B 沿 `blockedBy` 走，遇到 A 即拒绝；菱形依赖不会误报。
- 门禁位置正确：在合并前、rebase 前检查，所以被阻塞的工单不会被无故 rebase；面板和主会话走同一个 `mergeTicket`，都受约束。
- 阻塞工单被丢弃时给出“永远不会合并，请先移除依赖”的可操作提示；未知 id 按“未合并”处理，不会静默放行。

## 6. 已知范围（未改）

依赖的增删没有写进本地工单的 Markdown 归档，也没有 crash 后的补写；归档记录的是请求、结束与合并等生命周期事实，依赖是合并顺序的编辑。这一点在 00069 的范围里没有写明，这里补记，避免误以为它会出现在归档里。
