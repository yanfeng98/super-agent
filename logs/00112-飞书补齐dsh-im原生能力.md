# 飞书补齐 dsh-im 原生读取能力

## 1. 目标

上一版把飞书入口交给 dsh-im 后，superagent 只剩一条纯文本通道：不能补收、不能看图、看不到机器人消息、没有原消息链接、重试可能重复回复。这一版把旧 lark-cli 飞书的实现原理搬进 dsh-im 的 SDK 层，不再引入 lark-cli 或第二份凭据。

## 2. dsh-im 侧

- `normalizeExternalText` 支持 `post`（富文本渲染成文本，`@` 用名字、图片写成 `[图片] img_xxx` 以便回读）和 `image`（`[图片] img_xxx` 占位）；`includeBots` 为真时放行 `app`/`bot` 发送者，事件 `actor.kind` 为 `bot`，只有 `app_id` 的机器人也能识别；post 里的 `@` 元素也参与“是否 @ 了机器人”的判断。
- `consumeInbound` 接受 `includeBots`，并把它记在独占消费者上；`acceptExternal` 按该消费者决定是否放行机器人消息。
- 新增 `dshIm` 方法：
  - `chatHistoryChecked(botId, { chatId, since, until, cursor, limit, includeBots, direct })`：按时间范围读一个群/私聊，最旧在前；
  - `threadHistoryChecked(botId, { chatId, threadId, since, cursor, limit, includeBots })`：按时间范围读一个话题；
  - `messageChecked(botId, route)`：读一条消息并返回 `message_app_link`；
  - `chatMembersChecked(botId, { chatId })`：读群成员 open_id + 名字；
  - `resourceChecked(botId, route, { fileKey, type, maxBytes })`：按上限下载图片/文件字节。
- `replyChecked` 接受 `uuid`，重试时由飞书去重。
- 生产验证缓存 tenant token（按应用身份，10 分钟或按返回的 expire），每次仍读取机器人身份，所以远端身份变化仍会立即报 `account-changed`。
- 新增读取都要求独占消费者租约，并校验账号 fingerprint；`historyChecked` 的 `includeBots` 也已支持。
- 历史读取现在包含机器人消息（`includeBots`）和富文本/图片占位；机器人消息仍按 `sender_type` 标记，不会变成人类消息。

## 3. superagent 侧

- 新增 `src/sources/feishu-im-loops.ts`：
  - 每 60 秒按游标补收配置的群和已知私聊（首次回看 10 分钟），逐页读到没有 `nextCursor`；
  - 轮询已订阅线程，按线程游标补收；
  - 补收的消息与实时事件共用 Trigger id，`Intake` 去重，重叠不会产生重复工单；
  - 健康状态写入新增的 `history` 条目；
  - 每轮把 dsh-im 的群投递目标名称合并进 `KV.sources.labels`，群名会随补收自动更新；
  - 游标只在读完整页后推进到 `now`（回退 5 秒）；达到单轮页数上限时推进到最后一条消息（同样回退 5 秒），不会跳过窗口，也不会因最终一致性漏消息。
- `imTrigger` 用 `withMentionNames` 把 `@_user_1` 换成 `@名字`；机器人发送者 `human: false`；`meta` 记录 `messageType`、`images` 和 `bot`。
- 上下文消息（`eventView`）同样替换 `@` 名字，并带上 `bot` 标记和 `reply_to`，模型能分清谁说的、在回复谁。
- 图片：`readFeishuImImage` 通过 `resourceChecked` 下载、按魔数判断 PNG/JPEG/GIF/WebP，再作为附件交给模型；`threadContext` 恢复 `images`/`image` 钩子。
- 策略恢复 `bots`（机器人消息作为候选）和 `syncChat`（从群成员同步允许名单）。
- 来源链接：`sourceLink` 先通过 `messageChecked` 取原消息 AppLink，失败再退回 `feishu-im/<trigger>/thread` 资源。
- `refreshLabels` 现在会把读到的名字写入 `KV.sources.labels`，面板的群名选择器不再总是空。
- 回复：`sendFeishuIm` 用消息 id 作为 `uuid`；`reply-result-unknown` 交给 outbox 重试，同一 `uuid` 由飞书去重，既不丢回复也不重复。
- 机器人品牌按 `botId` 缓存，切换机器人后旧工单的 Lark/Feishu 链接不会用错域名。
- 历史与实时事件都带 `includeBots: true`，机器人消息进入评估前仍受 `policy.bots` 约束。

## 4. 行为与限制

| 场景 | 结果 |
|---|---|
| superagent 或 Host 重启 | 下一轮补收按游标读回缺失消息，实时与补收按 Trigger id 去重 |
| 用户在群里发图片 | dsh-im 渲染为 `[图片] img_xxx`；评估可调用图片读取，按权限和模型能力下载 |
| 富文本（post） | 渲染为标题 + 段落文本，`@` 用名字、图片保留 key；post 里 @ 机器人也算 addressed |
| 群里的机器人消息 | 实时与补收都可见；只有 `policy.bots` 名单里的机器人能成为候选，且不能发起明确请求 |
| 重试回复 | 同一消息 id 作为 `uuid`，飞书去重；结果不确定时重试而不是丢弃 |
| 读取全部群消息 | 仍取决于飞书应用权限（`im:message:readonly`、`im:resource`、获取群组中所有消息） |

独占模式不变：接管期间 dsh-im 自己的卡片、斜杠命令和普通会话仍暂停。

## 6. 审计修复

实现完成后又逐项自查了一遍，发现并修复以下问题：

- **post 图片读不了**：`renderPostElement` 只输出 `[图片]` 不带 `img_` key，`readFeishuImImage` 的 key 校验永远失败；改为 `[图片] img_xxx` 并补测试。
- **post 里 @ 机器人不算 addressed**：`message.mentions` 可能为空；渲染时收集 `@` 的 user_id，参与 `mentionedAccount`。
- **只有 `app_id` 的机器人发送者被拒**：`normalizeExternalText` 只读 `sender_id.open_id`，会抛 `invalid-inbound` 丢掉整条消息；`includeBots` 时回退到 `app_id`。
- **上下文丢标记**：`eventView` 不替换 `@`、没有 `bot` 和 `reply_to`；补齐。
- **结果不确定的回复被静默丢弃**：`reply-result-unknown` 原来当成已发送；改为交给 outbox 重试，靠 `uuid` 去重。
- **补收游标跳过窗口**：达到单轮 20 页上限时仍把游标推到 `now`，剩余消息永久丢失；改为只推进到实际读到的最后一条（回退 5 秒）。
- **多机器人品牌串用**：`cachedBot` 单例导致旧工单链接可能用错 Lark/Feishu 域名；改为按 `botId` 缓存。

## 8. 与旧 lark-cli 飞书的差距修复

旧实现（`src/sources/feishu.ts` 的 lark-cli 通道）仍在仓库里，但 `package.json` 的 exports 已不再暴露它，任何 profile 都不会加载。这一轮按逐项对照补齐它独有的能力。

dsh-im 侧：

- `replyChecked(route, text, { uuid, format, replyInThread })`：`format: 'markdown'` 用 schema 2.0 卡片发富文本（与 dsh-im 主动发消息同一个渲染器），`replyInThread` 显式控制是否进话题，默认仍按源消息是否已在线程里决定。
- **可以回复机器人发的消息**：发送者校验改用 `senderMatches`，人类按 `open_id` 比对，机器人/应用消息按 id 比对。旧实现没有这个限制，而 Policy 的 `bots` 名单本来就允许机器人消息成为候选，之前这类工单的回复会被判成 `stale-route` 静默丢弃。
- `messageChecked(botId, route, { messageId })`：读同一会话里的另一条消息（回复的父消息、话题根消息）。保留的 route 仍证明调用方有权读该会话，目标必须属于同一 `conversationId`。
- 消息类型统一由 `MESSAGE_TYPES` 放行：`text/post/image/file/audio/media/sticker/interactive/share_chat/share_user/merge_forward`。后几种渲染成一行占位（`[文件] 名字 file_key`、`[语音] 3s file_key`、`[卡片] 正文`、`[合并转发]` 等），不再整条消失。
- 历史事件带 `appLink`（`message_app_link`），上下文消息恢复 `url`。

superagent 侧：

- `sendFeishuIm` 以 `format: 'markdown'`、`replyInThread: true` 回复，恢复旧版 `--markdown --reply-in-thread` 的行为。
- `root`/`parent` 上下文按 id 精确读取，父消息再远也能读到；已删除或发送者既不是人也不是机器人时返回 `no_parent`/`no_root`。
- 上下文消息带 `url`（AppLink）。
- 实时路径给 Thread 写 `threads.describe`（群名 + 群链接），面板不再缺群名。
- `linkTimeoutMs` 配置项恢复，链接解析用它而不是写死 5 秒。
- `DSH_SUPERAGENT_FEISHU_BOT` 在缓存里有名字时恢复成机器人名字，不再是裸 id。

## 9. 第二轮审计

提交后又按"这条校验还成立吗"逐项复查了一遍，发现并修复四个问题：

- **`messageChecked({ messageId })` 绕过了 route 校验**：原来只检查目标消息属于同一个 `conversationId`，route 本身没验证，伪造的 route 可以读到该会话里的任意消息。现在先按 route 取回源消息，用 `anchorMatches`（同会话、同作者、同话题关系、未删除）校验，再读目标；测试补了"错误 route 读不到"的断言。
- **补收路径不写 Thread 描述**：旧实现补收和实时两条路都会 `threads.describe`，新实现只在实时路径写，补收产生的 Thread 没有群名和群链接。`BackfillDeps` 新增 `describe` 回调，补收时同样写。
- **单条消息读取丢了话题字段**：`messageChecked` 只返回文本和链接，`root`/`parent` 上下文里的 `reply_to` 因此丢失。返回值补 `threadId`/`rootId`/`parentId`，`messageView` 映射成 `reply_to`。
- **测试用的 route 与 anchor 不一致**：root/parent 的测试用人类 actor 去读机器人 anchor，恰好掩盖了第一点；改成用机器人 route，并保留错误 route 的拒绝断言。

## 11. 第三轮：剩余的四处差距

上一轮报告里还剩下的功能差距按「1 → 2/3 → 4」实现，顺带把几条可靠性问题一起补了。

dsh-im 侧：

- `resourceChecked` 接受 `messageId`：下载同一会话里另一条消息的图片/文件。先用 `readExternalMessage` 校验保留的 route（`anchorMatches`），再读目标消息并要求同会话，最后才用目标消息 id 下载；伪造的 route、跨会话的目标都读不到。
- 新增 `chatListChecked(botId)`：`im.v1.chat.list` 全部分页，返回 `{ chatId, name? }`。控制器、投递适配器、投递服务与 `dshIm` 服务同步转发。

superagent 侧：

- **上下文图片**：`readFeishuImImage` 把上下文消息的 id 传给 `resourceChecked`，父消息/根消息/话题里的图片都能读回；route 仍是 Trigger 自己的，越权由 dsh-im 的 anchor 校验挡住。
- **`around` 与 `message` 上下文**：`ContextPartName` 增加 `message`（按 id 重读源消息）与 `around`（消息前后各 5 条，话题里的消息也能读）；`feishu-im/<trigger>/{message,around}` 在 `orchestrator_read` 里可用，旧 lark-cli 通道因为共用同一个接口也一并恢复。
- **群名**：`refreshLabels` 与补收循环每轮合并 `chatListChecked` 的群名，再叠加 dsh-im 投递目标的名字，选择器不再只认投递目标；接管没打开时 `chatListChecked` 需要消费者租约，会退回投递目标的名字。
- **可靠性**：账号/消费者读取失败按 `consumerRetry` 从 1 秒退避到 60 秒（helper 移到 `poll.ts`，旧通道改为再导出）；健康条目改用 `imMissing`/`imBotUnset`/`imHandoffOff`/`imConsumerTaken`/`imBackfillMissing` 等 code，面板按界面语言显示；Thread 缺 `threadId` 时用 `messageChecked` 读根消息并 `threads.patch` 补上，再轮询；首次补收只记游标、不回看 10 分钟，避免把接管前 dsh-im 已经处理过的消息重新变成工单。
- **跳过计数**：补收与线程轮询把 dsh-im 的 `omitted` 汇总，健康里报成「N unreadable messages skipped」，与旧实现一致。
- **触发链接**：`imTrigger` 直接使用事件里的 `appLink`，不再多一次网络读取，超时也不会退成 `source_url_read`。
- **旧配置**：`readPageSize` 接受 1–50 但钳到 20，存着旧 lark-cli 的 50 不会让来源校验失败被静默停用。

## 12. 第四轮审计

逐条复查这轮的改动，找到并修复六个问题：

- **话题漂移导致回复被当成“消息已消失”**（dsh-im）：飞书在消息发出之后才给它补 `thread_id`——机器人自己用 `reply_in_thread` 回复、或别人在话题里回复都会触发。保留的 route 里没有话题 id，而 `anchorMatches` 原来要求话题字段完全相等，于是这类工单的回复被判 `stale-route` → `sendFeishuIm` 返回 `gone` 直接丢弃，上下文读取也一起失败。现在只在「这条消息本身成为该话题的根」时容忍这个单向变化（`root_id` 为空或等于消息自己的 id、`parent_id` 不变）；指向别的话题、或消息已在别人的话题里而 route 没有话题 id 仍然拒绝。`replyChecked` 改为复用同一个判断，不再各写一份。
- **退避窗口算进了等待时间**（superagent）：`runningSince` 在上一轮 delay 之前记录，于是 60 秒退避之后的下一次失败会把 `ranMs` 算成 60 秒以上、退避立刻归 1 秒，形成 1s→…→60s→1s 的振荡。改为只在真正开始一次尝试时记录起点。
- **没有名字的投递目标会覆盖已读到的群名**：`refreshLabels` 合并顺序里 `target.name || chatId` 会把 `chatListChecked` 读到的真名覆盖成 chat_id；改为 `target.name || labels[chatId] || chatId`。
- **`anchorMatches` 的文档与实现不一致**：注释说“容忍话题单向变化”，实现却只覆盖没有 root/parent 的顶层消息；补上「本身是回复、后来成为话题根」的情况并补测试。
- **Thread 话题查询每轮都打一次网络**：`learnThreadId` 对没有话题的订阅线程每分钟都会读一次根消息。改为按线程活动时间记结果（`KV.feishu.topic`），线程有新活动才再查；消息已消失（`stale-route`/`message-unavailable`）也记下来，其他错误仍重试。
- **`resourceChecked` 多读了一次锚点**：目标消息与 route 不同时，原来先读锚点再调用一次会重新校验锚点的读取，共三次请求；改为一次 `readExternalMessage(..., targetId)`，它本身就完成锚点校验与目标读取。

另外补了断言：话题漂移后 `scope: 'group'` 仍能读到该消息、`replyChecked` 仍能发送；而“route 没有话题 id、消息已在别人的话题里”仍然拒绝；无话题线程能从根消息学到 `threadId` 并 `threads.patch`。

校验：

## 14. 第五轮：再把三处内容差异修掉

第四轮之后又对读了一遍两条通道，剩下的差异按影响排序后修掉前三项，全部落在 dsh-im 侧（superagent 不用改代码，只改了两处文案）。

**1. 机器人自己的消息被当成新消息回灌（真实回归）**

旧 lark-cli 通道在 `feishuTrigger` 里用 `sender_id === botId || botAppId` 直接丢掉机器人自己的消息；dsh-im 的外部消费者只区分 user / bot，`includeBots` 又是补收必须开的（`bots` 名单要靠它），于是机器人每轮补收窗口里自己发出的回复（卡片、文本）会作为 Trigger 再进来一次。补收游标每分钟推进一次，所以这不是重启才有的事：只要机器人回过话，下一轮就会把它们收回来。

修法放在 dsh-im 的历史读取里（`readChatHistory` / `readThreadHistory` 共用 `readHistoryPage`）：发送者是本机器人（`sender_type: 'app'` 且 `id` 等于 `appId`，或 `sender_type: 'bot'` 且等于 `botOpenId`）时跳过，且**不计入 `omitted`**——否则健康里会报成“读不出来的消息”，把真实问题盖掉。上下文读取（`historyChecked` / `messageChecked`）**不过滤**：机器人的回复本来就是对话的一部分，读上下文时该看到。

**2. 合并转发只有一个占位**

飞书给 `merge_forward` 的 `content` 是固定文本（“Merged and Forwarded Message”），子消息要再调一次 `im.v1.message.get` 才拿得到。现在入站事件（`feishu-runtime` 的 `#withMergedForward`）和历史/上下文读取都会读一次子消息，渲染成 `<发送者>: <正文>` 行（正文按 text / post / 资源占位复用同一套渲染），读不到就保留 `[合并转发]`。入站路径上这是 ack 之前多一次网络调用，只对合并转发发生。

**3. 超长消息整条消失**

原来正文超过 16000 字符直接 `invalid-inbound`：实时事件被抛出后丢掉（连健康都不报），历史里算 `omitted`。改成截断——保留前 16000 字，结尾加 `[内容过长，已截断]`。顺带发现富文本渲染用了 `identifier()` 判正文，而它把 512 字符当上限，**长段落整段消失**；正文改用不受 id 上限约束的 `textValue()`。

superagent 侧只改文案：`policy.sync` 提示写回“启动时和点同步时进行”（启动时 `runtime.ts` 确实会对所有可同步来源跑一次），`readPageSize` 提示补“最多 20 条（dsh-im 单页上限）”。

## 15. 第五轮审计

逐条复查上一轮的改动，找到并修复四个问题：

- **入站合并转发会把事件确认拖过飞书的时限**（dsh-im）：`#withMergedForward` 在 ack 之前多读一次消息，而这次读取只受客户端 15 秒请求超时约束；租户网络慢时回调可能超过飞书的应答窗口，事件被重投（触发 id 相同不会重复成单，但会重复投递）。改为这次读取自带 2 秒截止（`MERGED_FORWARD_READ_MS`），超时就用占位，不拖慢确认。
- **子消息归属可能张冠李戴**（dsh-im）：`readMergedForward` 在拿不到 `upper_message_id` 匹配时会退化成「除自己以外的所有项」，如果响应里的项其实挂在**另一个** `upper_message_id` 上，就会被当成这条合并转发的正文。改为：有任何项声明了别的 upper message 时返回空（保留占位），只有整批都没有链接信息时才用退化规则。
- **截断会切坏代理对**（dsh-im）：`bounded` 按 UTF-16 长度 `slice`，第 16000 个码元正好是 emoji 的高代理时会留下半个字符。改为切点落在高代理上时再退一位，测试用 `isWellFormed()` 断言。
- **取消被当成读取失败吞掉**（dsh-im）：`expandMergedForward` 的 `catch` 连 `AbortError` 一起吞，取消后仍会返回半份上下文；改为先 `signal.throwIfAborted()` 再退回占位（入站路径同样处理，运行时信号被中止时照常抛出）。

另外补了两条测试：入站路径的合并转发展开与读不到时的占位（`feishu-runtime.test.mjs`），以及子消息挂在别的 upper message 上时不被误用、嵌套 `sender.sender_name` 也能渲染（`history-reader.test.mjs`）。

## 18. 第七轮审计（自查）

对第 17 节的三项改动逐条复查，改了四处，其余确认无误：

## 20. 第九轮：补掉「会丢消息」的两条差距

上一节末尾「仍然没补的」里，两条不需要真机就能补，而且都只动 dsh-im 版来源自己（不碰 vendored 的 dsh-im），这一轮补掉。

**话题回复不再漏收。** 飞书的群历史容器只返回「话题被打开的那条消息」，话题里的后续回复只在话题容器里。老 lark-cli 版靠 `backfillChat` 的两段扫描补上：先扫群，把带 `thread_id` 的消息记进话题表，再对表里每个话题按话题容器扫一遍。dsh-im 版的补收只读配置群、已知私聊和已订阅的 Thread，于是「群在全部消息模式下、话题里有人 @ 机器人、没有开票因此没有订阅 Thread、恰好发生在 superagent 重启期间」这一类消息会永久丢失，实时路径不受影响。

现在 `backfillChat` 把每条消息的 `reply.threadId` 记进 `KV.feishu.imTopics(chatId)`：话题 id 对应「最近一次群内可见活动」和「这个话题的根消息 id」，每轮按本轮时间窗（`since` 到 `until`）用 `threadHistoryChecked` 把这些话题各自读一遍再走 `ctx.receive`。三条约束保证它不会失控：已订阅 Thread 覆盖的话题跳过（那个由 Thread 轮询负责，避免同一话题每轮读两次）；`POLL_HORIZON_MS`（14 天）没有动静的话题丢掉；每群每轮最多读 20 个话题，按最近活动排序。单个话题读失败只记进本轮的 `history` 健康（最多 3 条，其余计数），不阻塞这个群的游标——否则一个读不了的话题（dsh-im 的 `threadHistoryChecked` 要求每条消息的 `thread_id` 等于话题 id，比老版严格）会把整个群的补收永久卡住。

**补收吞吐。** 单页从 `readPageSize`（最多 20）改成 dsh-im 允许的上限 50，每轮页数 20 → 40，即每群每轮最多 2000 条（原来 400 条）。忙群停机两小时的补齐从十几分钟降到几轮。`readPageSize` 仍然是「智能体读线程和群历史」的每页条数，不再顺带决定后台补收。

**话题历史改成正序。** `/thread` 读话题改走 `threadHistoryChecked`（正序、游标分页），不再用 dsh-im 的 `historyChecked({ scope: 'thread' })`——那个写死 `sort_type: 'ByCreateTimeDesc'`，而老版是正序。倒序不只是读起来别扭：`admissionContext` 最多读 10 页（200 条）拼评估窗口，长话题里触发消息通常是话题第一条，落在窗口外就 `source_found: false`，评估看不到发起工作的原话；`prompts/admission.md` 写的「窗口是前五条线程消息加触发前后各五条」本来就假设窗口从头开始。没有 `threadHistoryChecked` 的旧 dsh-im 回退到原来的倒序读法，不报错。

自查改了四处：

- **自己引入的回归**：`part === 'thread'` 但没有话题的触发消息必须继续走 `nearby`，否则 dsh-im 会以 `thread-unavailable` 拒绝。分支重构时丢了这个条件，补了 `reads the chat around a message that sits in no topic` 用例守住。
- **私聊话题**：`threadHistoryChecked` 的 `direct` 要透传（`dsh-im.ts` 的类型补上 `direct?`）。否则私聊话题里恢复出来的消息会被标成群消息，`scope` 判成未列出的群而被丢弃。
- **话题的 Thread 归属**：话题容器返回的消息可能没有 `root_id`，这时用「发现该话题的那条群消息」（有 `rootId` 就用它）当根，保证补收开的 Thread 和实时路径开的是同一个；否则会多出一个以 `threadId` 为根的 Thread，工单挂在两条线上。
- **词表门禁**：`tests/model-surface.spec.ts` 把 `topic` 列为模型面文的遗留词，技能文案里补的「a Topic from its first message」被拦下，改成 `Thread`。

新增测试三条：话题正序读取（含游标透传、旧 dsh-im 回退由既有用例覆盖）；话题回复补收（无 `root_id` 的消息归到同一个 Thread、话题表落库、健康计数）；已订阅话题不重复读。改一条：`counts the messages dsh-im could not render in the history health` 改用不属于任何话题的消息，免得本轮多出来的话题读把「2 条不可读」算成 4 条。

审计又查出三处，都补了：

- **页预算用尽会永久丢掉话题剩下的消息**。话题读和群读不一样：群有游标，读到哪存到哪；话题原来每轮都按本轮窗口从头重读，40 页没读完就直接结束，下一轮的窗口已经越过那段，剩下的消息再也读不到。改成话题表里加 `readThrough`：读完一轮存 `until`，页数用完就存最后一条投递消息的时间，下一轮从那里（前推 5 秒）接着读。
- **读失败且一条都没投递时，窗口会被标成已读**。加了 `readThrough` 之后，「没读完 → 存最后投递的时间」在「一页都没成」时无值可用，代码会退回「窗口读完」，于是一次瞬时失败就把这段窗口永久跳过。改成：失败且没有进展时保留原窗口，下一轮重试。
- **`recoverTopics` 抛错会丢掉整个群的这一轮补收**。话题读的失败已经在单个话题里接住，但 `threads.subscribed` 之类的意外异常会冒到上层，群游标此时已推进，这一轮的窗口就丢了。改成把它包进 `try`，记进本轮的 `history` 健康。

两条回归用例（`resumes a topic from the last message it delivered…`、`keeps a topic's read position when the read fails…`）都先验证过「去掉修复就失败」，不是只跟着实现走。`backfillChat` 为此外导出（老版的 `feishu-loops.ts` 也是导出的），并在 JSDoc 里写明参数和返回。

## 21. 第十轮：独立审查又查出七处，全部修掉

把这一轮的改动交给一个独立审查（对照老版 lark-cli 实现和 dsh-im 的真实读取语义），查出七处问题，其中两处会让人在飞书里的回复彻底丢掉。

- **给恢复的消息伪造 `root_id`，这条 Trigger 之后的所有读写都被判 `stale-route`**（最严重）。我原来给缺 `root_id` 的话题消息补写 `event.reply.rootId`，而 `imTrigger` 把它放进 Channel 地址（`routeAddress`）。dsh-im 的 `anchorMatches` 要求路由里的 `threadId`/`rootId`/`parentId` 与消息真实字段一致，只容忍「消息后来成了话题根」这一种单向变化，而且要求路由里两个字段都没有；伪造的 `root_id` 既不等于消息的 `root_id`（多为空），也过不了这条豁免。后果是这条消息之后的 `historyChecked`、`resourceChecked`、`replyChecked` 全部 `stale-route`，而 `sendFeishuIm` 把 `stale-route` 映射成 `gone`，outbox 就此结案不再重试——人在这条话题里回复，既不会被确认也不会被回答，图片文件也读不出来。改为：**路由保持 dsh-im 报告的原样**，话题根只用来决定 Trigger 落在哪个 Thread（`imTrigger(event, root)` 的第二个参数）。

- **同一个话题裂成两个 Thread**。飞书给「被回复的那条消息」只加 `thread_id`、不加 `root_id`，而话题里的回复把那条消息记成 `root_id`；`imTrigger` 原本用 `rootId ?? threadId ?? messageId`，于是话题根落在 `oc:omt_…`、回复落在 `oc:om_root`。`intake` 只按 Trigger 自己的 Thread 分发，挂在根消息 Thread 上的工单就永远收不到这个话题的回复，Thread 轮询也只喂另一条。老版 `feishuThreadId` 用 `rootId ?? messageId`，所以没这个问题。改成同样取 `rootId ?? messageId`，补收时再把话题根作为第二参数传进去，覆盖飞书漏报 `root_id` 的回复。

- **只读最近活动的 20 个话题会把老话题饿死**。`at` 只在被读到或有群消息带 `thread_id` 时前进，而话题回复不进群历史；掉出前 20 的话题再也读不到，14 天后连同没读的回复一起被剪掉。改成按 `readThrough` 最旧优先，每轮每个话题都往前走一步。

- **上一版写下的 `{at, rootId}` 会让话题永久读不出来**。加 `readThrough` 之后老条目缺这个字段，`Date.parse(undefined)` 抛 `RangeError`，被单个话题的 `catch` 接住，又把同样的形状写回去，于是每轮都失败直到被剪掉。把 `readThrough` 改成可选，缺省按本轮群窗口起点读。

- **「已订阅就跳过」跳得太宽**。Thread 建出来时 `meta: {}`（`part.ts`），话题 id 通常只在最新 Trigger 的 `meta.threadId` 上，靠 `learnThreadId` 才补进 meta，所以绝大多数已订阅话题其实被重复读；另一边，超过轮询期限、根本不会被轮询的 Thread 也被算作「有人管」，让 `recoverTopics` 永久跳过它的话题，直到被剪掉。改成只看本轮真正会被轮询的 Thread（`polled`），并补上 Trigger 的回退。

- **一轮补收没有时间上限**。一个群最多 40 页群读 + 20×40 页话题读，每页还有 30 秒超时，慢的时候一轮能跑很久，健康状态跟着长时间不更新。加了每轮 5 分钟的时间预算（`ROUND_MS`），到点就停，进度按游标/水印留给下一轮。

- **中断可能丢掉刚发现的话题**。群游标先推进、话题表只在轮末落盘；若在话题读期间被中断，发现话题的那条群消息已在游标之后、话题表又没写，回复就永远收不到了。改成先落盘话题表，再推进群游标。

已存在的数据要知道一件事：上一版可能把某些话题根消息的 Thread 记成了 `oc:omt_…`（根消息在话题已经存在之后才被补收时），这些 Thread 本来也收不到话题里的回复（回复一直落在 `oc:om_root`），所以不构成回归，但也不会被这次修复回填——新的票据从根消息的 Thread 开始接话题回复。

另外独立审查指出「页数用尽且一条都没投递」时我把窗口标成已读，其实那可能是「前 2000 条都不可读/都是机器人自己发的」而不是读完了。改成保留窗口重试。代价是这种病态话题每轮重复读 40 页（有界、与其他话题轮流、不丢消息），已知取舍。

## 22. 第十一轮：修掉「语义对不上」的四条

上一轮把剩下的差距分成四类，这一轮修掉第二类里能在本地收口的四条（对照物：老版 `feishu-read.ts`、`docs/008-cookbook.md` 对 `body` 的承诺、dsh-im 的 `history-reader.mjs`）。

- **撤回的消息能认出来了**。dsh-im 的 `readExternalMessage` 原来把「消息被撤回」和「路由不再指向原消息」一起报 `stale-route`，接管方只能都当「没有内容」。现在撤回单独返回 `message-deleted`（`history-reader.mjs`），主智能体映射成 `deleted` 状态；`unavailable` 表示正文读不出来或路由不再解析；`no_root`/`no_parent` 只用于「路由里本来就没有这个字段」。dsh-im 的 CHANGELOG 记了这一条。

顺手修掉上一轮留下的一处注释错误：`TOPIC_READS_PER_ROUND` 上面写的是「most recent first」，实际按最久未读优先排，改成 least recently read first。

## 23. 第十一轮审计：又查出四处，其中一处让 `deleted` 在真实路径里失效

把 §22 的改动逐条对照 dsh-im 的真实调用链（不是测试里的 stub）复查，查出四处：

- **交付层把 `message-deleted` 洗成 `history-unavailable`**（最严重）。超级智能体拿到的 `ctx.get('dshIm')` 是 dsh-im 的 `DeliveryService`（`plugin-src/host/index.mjs`），它的 `#checkedAdapterRead` 只保留 `DELIVERY_ERROR_CODES` 里的码，其余一律换成 `history-unavailable`。我新加的 `message-deleted`——以及本来就在用、原来也不在名单里的 `message-unavailable`——因此到不了 `readMessage`，撤回消息会被当成未知错误抛出，`deleted` 状态只有在直接 stub 服务的单测里成立。修：两个码加进 `DELIVERY_ERROR_CODES`，新增 `test/delivery-checked-read-codes.test.mjs`，用真实 service 加一个只实现必需方法的假适配器验证「具体码保留、内部码仍被洗成 `history-unavailable`」。

## 24. 第十二轮审计：`deleted` 的适用范围写宽了，运行时不用改

按消费者的真实调用形状（总是带 `messageId` 读）用真实的 `readExternalMessage` 实测三种情况：

| 场景 | dsh-im 返回 | 主智能体状态 |
| --- | --- | --- |
| 父消息被撤回、源消息还在 | `message-deleted` | `deleted` |

## 26. 第十三轮：上下文窗口里的「自己」和「撤回」

上一轮回答「还有哪些差距」时对着代码又查出两条，都不在 §25 的清单里，本轮修掉。

### 两条差距

- **话题线程的上下文读不到机器人自己说过的话**。superagent 读 Thread 上下文时，消息带话题 id 就走 dsh-im 的 `threadHistoryChecked`；而 `readHistoryPage` 是给补收写的，里面有一条「自己的消息直接跳过、也不计入 `omitted`」。老版的 topic 页把机器人消息以 `bot: true` 留在页面里。结果是同一个 Thread，有话题 id 时看不到自己以前的回答，退化成「群邻近窗口」时又看得到（邻近读法 `readExternalHistory` 从来没跳自己的消息）。评估窗口和 `orchestrator_eval_read` 因此分不清「这条已经答过」和「没人接」。dsh-im 的 CHANGELOG 说「context reads 仍显示它们」，那句话对 `historyChecked` 成立，对实际用作上下文读法的 `threadHistoryChecked` 不成立。

## 27. 第十四轮审计：撤回源消息的读法，以及窗口状态要能看见

对 §26 的改动逐条核对，代码本身没问题，但顺着它核对「源消息被撤回后哪些读法还读得到」时，查出文档写宽了，而且 `/around` 的返回与按 id 的读法不一致。

### 核对结果（未发现缺陷的部分）

| 核对项 | 结论 |
| --- | --- |
| 选项名与语义在两侧一致 | dsh-im 读 `includeSelf`/`includeDeleted`，superagent 传同样的键；交付层 `structuredClone` 原样转发 |
| 默认行为 | `includeSelf`/`includeDeleted` 缺省为假时，补收与老版逐条一致（自己的消息跳过且不计数、撤回消息计入 `omitted`） |
| 补收不受影响 | `feishu-im-loops.ts` 不传这两个选项，自己的回答不会变回 Trigger、撤回消息也不会开新工单（本轮加了断言） |
| 老版本 dsh-im | 旧读法忽略未知 query 字段，窗口照常读，只是没有这两类条目 |
| 撤回占位的事件字段 | 保留发送者、时间、reply route，`text` 空、`deleted: true`；缺 id/时间时只计数（本轮加了用例） |
| 撤回占位与 `includeBots` | 机器人发的撤回消息仍受 `includeBots` 约束，与活消息一致 |
| 构建产物 | `lib/index.js` 里确有占位事件与两个选项；superagent 的 `feishu-im-*` chunk 也传了 `includeSelf`/`includeDeleted` |

### 缺陷一：文档说「源消息被撤回后整条 Trigger 的读取都是 `unavailable`」

实际上 `/thread` 走的是 `threadHistoryChecked`，它按 threadId 列话题历史，**从不校验保留的 route**（`readExternalHistory` 才校验 anchor）。所以源消息被撤回后：

- `/message`、`/root`、`/parent`：`readExternalMessage` 带 `messageId`，先过 `anchorMatches`，撤回即 `stale-route` → `unavailable`；
- `/around`：走 `historyChecked` 的 nearby，同样校验 anchor，撤回即 `stale-route`，但 `feishu-im.ts` 当时直接把它抛给模型，而不是像按 id 读法那样回答 `unavailable`；
- `/thread`：话题列历史，无 anchor 校验，读得到；本轮之后还会把被撤回的源消息显示成 `deleted` 占位。

NATIVE、技能、`003-execution.md`、`006-deployment.md` 都写成「每一条读取都 `unavailable`」，等于把话题读法也算进去了。

### 缺陷二：把 `/around` 映射成 `unavailable` 之后，评估 payload 会看不到它

`admissionContext` 一直算出了 `status`，但 `assessment.ts` 拼 payload 时丢弃（§25 记录的老问题）。在 `/around` 抛错的年代，模型至少看到 `thread: { error: … }`；改成 `unavailable` 之后，payload 会变成一个 `complete: true`、`loaded_messages: 0` 的空窗口，看起来像「这段对话没有内容」。

### 缺陷三（本轮自查）：新用例被我插进了另一个用例内部

补 dsh-im 用例时锚点选错，新的 `test(...)` 落在了上一个用例的函数体里。`node:test` 会把它当子测试跑，所以「21 个用例通过」看起来没问题，实际顶层用例数没变、断言只是在别人的用例里顺带执行。改成顶层用例后重新跑过。
