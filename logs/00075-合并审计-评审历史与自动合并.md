# 00075 — 合并审计补全、评审历史与自动合并

- **日期**：2026-11-19
- **背景**：与 GitHub PR 工作流对照后剩三块差距：合并记录没有“谁/从哪条界面来”、评审只有最新一条且不留历史、以及“等检查通过就合并”必须等人再说一次。这轮把三件都实现了。
- **范围**：`src/core/model.ts`、`src/core/tickets.ts`、`src/core/engine.ts`、`src/core/errors.ts`、`src/app/runtime.ts`、`src/app/passes.ts`、`src/app/review.ts`、`src/app/tools/main.ts`、`src/app/http.ts`、`src/app/api.ts`、`src/app/views/tickets.ts`、`src/sources/local.ts`、`src/client/ticket.tsx`、`src/client/locales.ts`、`docs/001`–`007`、`README.md`、`NATIVE.md`、`tests/`。

## 1. 合并审计：界面、结果提交、推送结果

- `Ticket.merged` 新增 `via`（`chat` / `panel` / `auto`）、`head`（合并后目标分支所在的提交）和 `push: { at, ok, error? }`。
- `mergeWorkspace` 合并后多读一次 `rev-parse HEAD` 返回 `head`；读不到不影响已经完成的合并。
- `Runtime.mergeTicket` 增加第 4 个参数 `origin`（默认 `panel`），主会话工具传 `chat`，自动合并传 `auto`；面板 API 不传，走默认值。同一个工单的合并加了一个在跑标记，主会话的请求和自动请求不会同时对同一 worktree 跑 git。
- push 失败不再只出现在聊天回复里：结果写进 `merged.push`，并在本地归档追加一节 `状态: push-failed` / `error:`；合并本身照旧成立。
- 面板历史行显示“主会话 / 面板 / 自动”，合并行显示提交短 SHA 和推送结果。

## 2. 评审历史与提交锚定

- 新增 `Ticket.reviews`（最多 50 条，含 `at`、`decision`、`note`、`head`、`via`）：每轮评审都留着；`Ticket.reviewed` 仍是“拦不拦合并”的那一条，恢复、重开或变基时照旧清掉，但历史不动。
- 评审时记录当时 `review.head`，即这次评审覆盖的提交；面板历史与归档的评审节都会带上 `commit`。
- 备注（`TicketNote`）新增 `commit`：写入时取当前 `review.head`；面板在提交变化后给这条备注打“代码已变动”，备注仍然阻塞合并，由人决定是否解决。

## 3. 自动合并（standing merge request）

- 新增 `Ticket.autoMerge: { at, strategy?, cleanup?, push?, attempts, last?, next? }` 与工具 `orchestrator_ticket_automerge`（`cancel: true` 取消），主会话工具数 18 → 19。
- `Runtime.runAutoMerge` 由 pass 触发：找到到期的请求，走 `mergeTicket` 的同一套闸门（依赖、评审、备注、CI、检查、自动变基/冲突交回），合并后清掉请求并通过 `sessions.notify` 告知主会话。
- 闸门没过时记录 `last.error`，按 60s → 120s → 240s → 480s → 900s 递增等待，`next` 之前不再重试（避免每次 pass 都重跑检查）；第一次被拦会通知主会话，之后安静重试，第 8 次放弃并通知。
- 请求会跨重启存活（存在工单上）；工单重新 end 之后尝试计数清零、立即重试；人 `stop` 工单或丢弃工作区会清掉请求；面板可以查看并取消（`POST tickets/:id/automerge`）。
- 已知取舍：取消/停止只能阻止“还没开始的尝试”，正在执行的合并照旧完成——与 GitHub 取消 auto-merge 的语义一致。

## 4. 测试

- `tests/merge.spec.ts`：记录 `via`/`head`/推送失败；`chat` 来源；自动合并在 pass 里完成、依赖未合并时等待并记录原因且到期前不重试、8 次后放弃、取消与人 stop 清空。
- `tests/core-engine.spec.ts`：两轮评审都保留、`reviewed` 与 `reviews` 的差异、备注带上提交、重开后历史还在。
- `tests/chat-tools.spec.ts`：自动合并工具的登记参数与取消。
- `tests/views.spec.ts`、`tests/panel-execution.spec.tsx`：历史里的界面标记、提交、推送结果，以及备注“代码已变动”。
- 模型面预算：新增一个工具后实测 62,285，`BUDGET.orchestrator` 由 61,100 调到 62,400。

## 5. 提示词与测试期望

- `prompts/orchestrator.md` 原来写 “never merge otherwise, enable auto-merge”，在有了“登记后自动合并”之后会自相矛盾。改成：合并只在人于本对话明确要求时发生，`orchestrator_ticket_merge` 表示现在合，`orchestrator_ticket_automerge` 表示之后再合；仍然禁止自行启用 GitHub 的 auto-merge。整份提示词 1,399 / 1,400 字符，`tests/cards.spec.ts` 的断言同步更新。

## 7. 仍然存在的差距

- 评审没有“谁”的字段（单人操作，界面来源是主要信息）；没有按人分配的评审人、CODEOWNERS 或多人批准。
- 没有回退已合并工单的操作；没有合并队列；合并后不对目标分支再跑一次检查。
- 笔记只能按单行锚定，不能区间标注或建议修改；diff 仍是整段字符串。
