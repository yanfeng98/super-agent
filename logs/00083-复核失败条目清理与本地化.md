## 1. 失败条目在工单被别处合并后会永远滞留（已修）

- 问题：失败条目会一直留在队列等重试；如果它的工单被人在聊天/面板合并（或丢弃、清理）了，重试永远失败，条目和旧原因就一直挂在面板上，只能手动移出。
- 修复：`Runtime.pruneMergeQueue` 在每次排空前清掉“工单已不存在/已合并/已丢弃/已清理”的失败条目；`runMergeQueue` 在判断“有没有可跑的条目”之前调用它，所以只有失败条目时也会执行。
- 测试：合并后跑一次排空，条目消失。

## 2. 第一版清理条件过宽，会误删“被交回后重新打开”的条目（自审中修掉）

- 问题：最初的条件写成“未结束即清理”，而 rebase 冲突会把工单交回给 worker（工单重新变成 open），它之后还会再次结束——那条排队请求会被误删。
- 修复：只清理“工单不存在/已合并/已丢弃/已清理”的条目；open 的工单保留条目（带原因），等它再次结束并重试。
- 测试：失败后把工单重新打开 → 条目保留；再次结束 + 重试 → 合并成功、条目消失。

## 3. 补上“拒绝码 → 面板文案”的端到端用例（补测）

- 上一轮把备注路由改成让 `UserError` 直接返回 `{ error, code }`，但没有测试证明面板真的会本地化。
- 面板测试夹具的备注路由现在按宿主规则拒绝“只有结束行没有起始行”，并返回 `code: invalidNoteRange`；新增用例断言弹出的提示就是 `userError.invalidNoteRange` 的中文文案（英文界面同理，因为走的是同一套字典）。

## 4. 复核后确认无问题的点

- `enqueueMerges` 整体替换条目：位置不变、选项更新、失败清除（上一轮的修复）。
- 回退保护：运行时与视图用同一条件（`reverted.at > merged.at`）判断“这次合并已被回退”，旧记录不会二次回退。
- 排空循环：按 id 移除、失败条目留位、后续条目继续、同一条目连续出现即停止。
- 区间备注：起始行必填、不能倒序；面板/API/发给 worker 的汇总一致。
- 备注路由不再包装 `UserError`，`failure()` 返回 `{ error, code, values }`。
