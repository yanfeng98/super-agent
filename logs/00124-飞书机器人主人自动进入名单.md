# 00124 — 飞书机器人主人自动进入 superagent 名单

- **日期**：2026-11-23
- **背景**：有人问「我在飞书发了信息为啥 superagent 没有反应」。状态库显示消息 19:40:04 到达、19:40:06 决策 `ignore`，原因是 `not_a_member`；同一时间 dsh-im 里该机器人已经是 `external-consumer`、`superagent: true`，消费者也已注册，说明入口链路是通的。真正拦下消息的是 superagent 自己：Feishu Source 的「能发起工作的飞书用户」名单为空，而默认准入里「名单外 · 私聊机器人」是 `ignore`。
- **追问**：既然 dsh-im 里已经打开「交给 Superagent」，而且只有一个人用，为什么还要在 superagent 再配一份名单。
- **结论**：机器人主人是打开交接触发开关的人，dsh-im 已经记录了他们（`ownerOpenIds`）。把这份身份交给 superagent，并在 Feishu Source 的名单同步里自动采纳，用户就只需要在 dsh-im 里打开开关，不再配置第二份名单。

## 2. 原因与判断

- **谁有资格**：dsh-im 的 `ownerOpenIds` 是配置机器人时登记的人，打开「交给 Superagent」的也是他们；superagent 再要一份 `ou_...` 只是同一事实的第二份拷贝。把它当作 Feishu Source 名单的初始值，既保留名单这个显式配置，又不再要求用户重复录入。
- **为什么放在同步里**：Feishu Source 本来就有「立即同步」（群成员）这个外部名单来源；启动时 `initialize()` 会对所有可同步来源跑一次。让同一个同步顺带采纳主人，就不需要新的启动钩子，面板的按钮也仍然只有一种语义：把外部名单拉进策略。
- **为什么 `ready` 要看配置**：原先只有填了「同步来源群」才认为可同步；现在只要选了机器人就有主人可采纳。`ready` 因此拿到来源配置，而不再只看策略片段。
- **为什么优先用 `inboundStatus`**：它是 dsh-im 的本地读数（不核验账号）。启动时用它取主人，离线启动不会被一次 Feishu 账号核验拖住；只有要读群成员时才走带指纹的 `describeBot`。
- **为什么只补不删**：同步把主人补进名单，但不会删除名单里的人。机器人换了之后旧主人仍会留着，需要时在面板里删掉；这一点比“猜哪些条目是自动生成的”更容易解释。

## 3. 行为

| 场景 | 结果 |
|---|---|
| dsh-im 里打开「交给 Superagent」，superagent 重启 | 启动同步把该机器人的主人加进 Feishu 来源名单；主人私聊或 @ 机器人即为明确请求，无需再配置 |
| 面板点「立即同步」 | 同样采纳主人；若设置了「同步来源群」，名单先变成该群成员，再补上主人 |
| 换绑另一个机器人 | 新主人的主人加入名单；上一台机器人的主人不会自动移除 |
| dsh-im 没挂载或版本较旧 | 同步报错并在 `sync:feishu` 健康项里重试；旧版 dsh-im 没有 `ownerOpenIds` 时退回 `describeBot` 的返回 |
