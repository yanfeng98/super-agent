# 00092 — 工单停止、评审收尾与检查重跑

- **日期**：2026-11-20
- **背景**：上一轮按“聊天布置 → worker 执行 → 说合并”的用法对了一遍 GitHub 的 PR 流程，剩下三个仍要回面板的收尾动作：停止/放弃工单、收评审备注与批准、只重跑检查。本轮把这三个动作接进聊天，并让等待合并的状态报告带上工单结局。
- **范围**：`apps/web/native/dsh-superagent` 的 `src/app/runtime.ts`、`src/app/tools/main.ts`、`tests/chat-tools.spec.ts`、`tests/model-surface.spec.ts`、`docs/003-execution.md`、`docs/006-deployment.md`、`docs/007-architecture.md`、`NATIVE.md`、`logs/`。

## 1. 停止与放弃

- 新增 `orchestrator_ticket_abandon`：`ticket_id` 接受 id 或 `T-0007`。
- 运行中的工单先走 `Tickets.stop`，结束当前 Assignment，并撤回标准合并请求；`discard: true` 时再走 `discardTicket`，删掉 worktree 和分支。两步可以一次说“不做了”，也可以先只停、之后再放弃。
- `Runtime.ticketId` 统一解析显示编号，三个新工具共用；`stopTicket` 在工单已合并、已丢弃或已清理时拒绝，避免删掉已经落地的分支。
- 停止后 worker 可能还在收尾；`discard` 失败会原样报错，工单保持已停止状态，可以稍后重试放弃。

## 2. 评审收尾

- 新增 `orchestrator_ticket_review`：
  - `approve: true` 走 `reviewTicket(..., 'chat')`，记录批准；开启 `executor.requireReview` 时，这就是聊天里“合并”所缺的那一步。
  - `resolve: true` 走 `resolveAllNotes`，清掉所有未解决备注；未解决备注本来会挡住合并，所以“备注 → worker 修 → 说合并”不再需要回面板点 Resolve。
- 面板的 **Request changes**、逐条回复和逐条解决仍保留；聊天只做批准和全部解决，避免把评审讨论压成一句命令。
- 评审记录带 `via: chat`，归档和工单历史能看出是主 Session 记的。

## 3. 检查重跑

- 新增 `orchestrator_ticket_check`：调用 `checkTicket`，在工单 worktree 里重跑配置的检查并记录结果，不触发合并。
- 检查 flaky 时不用再 `orchestrator_ticket_retry` 重开一个 Assignment，也不用回面板点 **Run check**；合并本身仍会在检查未通过时自动跑一次。

## 4. 等待合并的状态

- `pendingMerges.waiting` 增加 `outcome`（`completed`、`stopped`、`failed` 等）。`orchestrator_merge_queue` 无参时，主 Session 能看出某个工单是已停止/失败，而不是“可以合并”。
- 没有改变合并门本身：显式说“合并 T-0007”仍然可以合并一个已结束的工单，是否该合由人说；这里只修正状态报告的读法。

## 5. 工具面预算

- 三个工具加入后，orchestrator 模型面从 64,700 上限下的余量变成超出。压缩了 `orchestrator_route` 的 acknowledgement、`orchestrator_ticket_merge`、`orchestrator_merge_queue`、`orchestrator_ticket_automerge`、`orchestrator_ticket_dependency`、`orchestrator_ticket_revert` 等既有描述，并把评审工具收敛为 `approve` + `resolve` 两个开关。
- 实测 65,372 字符（prompt 42,570 + tools 22,802），上限从 64,700 调到 65,500。

## 6. 测试与验证

- 插件测试：68 个文件 / **1391** 个用例通过（新增 4 个：停止/放弃、批准与解决备注、检查重跑、已停止工单的等待状态）。
- `tests/model-surface.spec.ts`：7/7，orchestrator 与 worker 都在预算内。
- `pnpm run test:docs`：21/21。
- `verify-client-ui-i18n`：1433 个文件通过（本轮没有改客户端文案）。
- 仓库 `pnpm run typecheck`：5/5；`pnpm run lint`：0/0；`pnpm run build`：12/12。

## 7. 仍然存在的差距

- 改名、标签、关联工单、编辑请求文本、单独 rebase、清理 worktree 仍只在面板；这些是记录或仓库操作，聊天入口的收益低于停止/评审/检查。
- **Request changes** 仍只在面板记录；聊天里“打回”用备注 + 发回 worker 表达，worker 修完再批准。
- 多人评审、CODEOWNERS、批准数、labels/milestones、draft PR、cherry-pick 和 release 分支仍不做：当前是单操作者部署。
- 合并目标仍是当前检出分支；队列串行，目标检查失败只暂停并通知。
