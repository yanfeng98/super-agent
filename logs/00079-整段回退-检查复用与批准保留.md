# 00079 — 整段回退、检查复用与批准跨变基保留

- **日期**：2026-11-19
- **背景**：单人使用视角的一次自审（00078 之后）发现三类真问题：fast-forward 合并的回退只撤销了最后一个提交；检查在自动重试中反复重跑、合并后还可能在操作者检出里留下脏改动；变基会把批准清掉，哪怕补丁没变。这轮修这三类。
- **范围**：`src/app/review.ts`、`src/app/runtime.ts`、`src/core/model.ts`、`src/core/tickets.ts`、`docs/003`、`docs/006`、`README.md`、`NATIVE.md`、`tests/`。

## 1. 修正：fast-forward 合并要整段回退

- 复现：分支上两个提交，ff 合并后用旧实现回退，只撤销了最后一个提交，前一个提交的改动仍留在目标分支上，而工单已标记“已回退”。
- `mergeWorkspace` 现在在合并前读目标分支的提交（`base`），并作为 `TicketMerge.base` 记录；第一次实现误用了 worktree 的 HEAD（等于工单分支），真实 git 测试抓到了这一点。
- `revertWorkspace` 增加可选的 `base`：给了 `base..head` 就逐个提交回退（`git revert base..head`），合并提交仍按第一父回退，冲突时 `git revert --abort` 恢复原状。
- `Runtime.revertTicket` 只在 ff 合并（没有记录策略）时传 `base`；squash / merge commit 仍只回退那一个提交。

## 2. 修正：推送重试要校验分支

- `pushWorkspace` 增加可选的目标分支：当前检出的不是这次合并移动的分支时直接拒绝（否则在别的分支上点“重试推送”，推上去的是那个分支，却记在这次合并上）。
- 合并当时的 push 与重试都传入 `merged.target`。

## 3. 检查策略

- **合并后检查**：fast-forward 合并后目标分支的树与工单分支完全一致时，跳过这次检查（闸门的检查已经覆盖同一棵树）；其余策略照旧在仓库根上跑。
- **脏检出提示**：目标检查跑完后若仓库出现已跟踪改动（检查命令自己写文件），留一条 `check` 通知提醒清理，避免下一次合并被“工作区有未提交改动”挡住。
- **失败复用**：自动合并的尝试在同一个 ending 下、10 分钟内已有失败记录时，不再重跑同一套检查，直接报告记录的失败（人工触发的合并仍会重跑）。

## 4. 批准跨变基保留

- 新增 `patchFingerprint`：对 `base..HEAD` 的 diff 取 sha256，代表“工单自己改了哪些内容”。
- `rebaseTicket` 在变基前后各取一次指纹：一致（只是把同一补丁挪到新提交上）就保留 `reviewed` 并把 `head` 指向新提交；不一致则照旧清掉批准。
- `Tickets.review` 把历史里的评审轮次存成副本，这样重新指向当前批准不会改写历史记录。

## 5. 测试

- `tests/review.spec.ts`（真实 git）：两个提交的 ff 合并整段回退；变基前后指纹一致、变更后不一致；仓库切到别的分支时拒绝推送。
- `tests/merge.spec.ts`：`merged.base` 与回退时传入的 base；重试推送传入目标分支；指纹一致保留批准（历史仍记旧提交）、不一致清掉；自动尝试复用已记录的检查失败且不调用检查命令，人工合并仍会重跑。

## 6. 文档与文案

- docs/003：回退整段语义、目标检查的跳过与脏检出提示、失败复用、批准跨变基保留。
- docs/006：revert 行说明 ff 逐个提交回退；push 行说明分支校验。

## 7. 仍然存在的差距

- 队列串行、失败即出队；没有多具名检查；评审注释仍是单行；没有“自上次评审以来的改动”。
- 回退后的工单仍是死路（不能再合并）；vendor 分叉已到 19 条本地修改。
