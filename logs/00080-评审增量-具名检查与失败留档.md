# 00080 — 评审增量、具名检查与合并失败留档

- **日期**：2026-11-20
- **背景**：单人使用视角剩下的三处摩擦：评审后又有新提交只能看全量 diff；一个检查命令说不清楚“哪一项挂了”；合并失败只留在聊天里，面板（也就是记录）看不见原因。
- **范围**：`src/app/review.ts`、`src/app/runtime.ts`、`src/app/check.ts`、`src/app/http.ts`、`src/app/api.ts`、`src/app/views/tickets.ts`、`src/core/model.ts`、`src/client/ticket.tsx`、`src/client/execution.tsx`、`src/client/locales.ts`、`docs/003`、`docs/005`、`docs/006`、`docs/007`、`README.md`、`NATIVE.md`、`tests/`。

## 1. 评审增量

- `GET tickets/<id>/diff?since=<commit>`：`Runtime.ticketDiff(id, since)` 以评审覆盖的提交为起点；路由只接受 7–40 位十六进制提交号，避免把任意 revision 传进 git。
- 工单页在“已评审的提交”与当前提交不同时多一个 **自评审以来的改动（短路哈希）** 按钮，只显示那之后的变化；查看全量的按钮仍在。
- “已查看”标记按“工单 + 提交 + 视角（全量/增量）”分开存，不会互相串。

## 2. 多条具名检查

- `executor.check` 仍然是同一个设置，但现在**一行一个命令**；写成 `名称: 命令` 就给这项检查起名（`parseChecks`，最多 8 条，冒号后必须有空格，所以 `pnpm test:unit` 不会被误拆）。
- 每项按顺序运行，`workspaceChecks` 把每项结果记在 `Ticket.checkRuns`，并合成一个 `Ticket.checks`（全部通过才算过，输出按 `## 名称` 拼接）——合并闸门、归档、历史都继续读这个合成记录，保持兼容。
- 面板的检查区块在有多项时列出每项的名称与结果；结束时的通知和目标分支检查失败的通知都会点名失败的检查。
- 设置页的提示文案改成“一行一个命令，`名称: 命令` 命名”。

## 3. 合并失败留档

- `Ticket.mergeError = { at, error, via }`：任何一次合并尝试失败都记录原因，合并成功后清除。
- 工单页展示“上次合并没有成功：……”，聊天滚过去之后仍能回看；自动合并/队列的失败也走同一条记录。

## 4. 测试

- `tests/check.spec.ts`：`parseChecks`（空、裸命令、`名称: 命令`、含冒号但无空格的命令）、`workspaceChecks` 逐项结果与合成记录。
- `tests/merge.spec.ts`：多行配置按解析结果调用检查、失败原因记录与成功后清除、`ticketDiff` 的 `since` 与默认 base。
- `tests/panel-execution.spec.tsx`：自评审以来的改动按钮发出 `since`、上次合并失败提示、逐项检查结果。
- 其余受 `workspaceChecks` 影响的地方改用新的 mock（`passingRuns`/`failingRuns` 辅助函数）。

## 6. 仍然存在的差距

- 队列串行、失败即出队；回退后的工单是死路（不能再合并）。
- 评审注释仍是单行锚定；没有多人协作身份（单人场景不需要）。
- vendor 分叉 20 条，router 提示词仍在 1,398/1,400 的边缘。
