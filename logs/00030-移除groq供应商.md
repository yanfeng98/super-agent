# 00030 — 移除 groq 供应商

- **日期**：2026-11-17
- **背景**：`groq` 是 pi-ai 目录里的推理云路由（Groq），默认端点 `https://api.groq.com/openai/v1`，使用 OpenAI 兼容对话补全，凭据为 `GROQ_API_KEY`，没有内置 OAuth 或订阅套餐入口。目录快照 7 个模型：Llama 3.1 8B、Llama 3.3 70B、`openai/gpt-oss-120b`、`openai/gpt-oss-20b`、`openai/gpt-oss-safeguard-20b`、`qwen/qwen3.6-27b`、`qwen/qwen3.8-27b`，全部是其他厂商的开源权重模型，Groq 只提供 LPU 推理硬件与托管。七个模型在其他内置路由上都能取到（全部在 `openrouter`，`gpt-oss-120b` 与 Llama 3.3 70B 另见 `together`），因此移除它拿掉的是一个托管面而非模型覆盖。用户要求移除该供应商且不能破坏现有功能，沿用既有的 `WITHHELD_PROVIDERS` 机制：目录、模型解析、发现、登录与可配置供应商列表都不再出现该路由，不修改 `node_modules` 里的 pi-ai 包。
- **范围**：`packages/llm/llm-pi-ai`（目录控制点与测试）、`docs/user/guide/providers.md`、包 README、升级指南、Web golden 与 e2e 断言、根 README、`logs/`。

## 2. 行为

- 可对话供应商 18 → **17**，目录模型 659 → **652**（只减 `groq` 的 7 个模型）。
- `catalogProvider('groq')` 返回 `undefined`，`catalogModels('groq')` 为空；目录、模型解析、发现、登录与可配置供应商列表都不再出现该路由。
- 存量 profile 点名 `groq` 时 `resolveProfiles()` 在 strict 与 deferred 下都抛 `llm-pi-ai: provider "groq" is removed from this build; delete the route or select another provider`，同一 `providers` 字典里的其他路由随之不可用，删除该条目即恢复。
- 内置 id 现为 42 = 17 个提供 + `typesafe` + 24 个被移除；`provider-data.generated.ts` 仍保留 42 个 id 的元数据（`verify-provider-data` 要求与已安装目录一致），它不是可售路由。
- `packages/experimental/webworker-runtime` 的 `BUILTIN_PROVIDER_IDS` 仍列出 `groq`：该列表描述 pi-ai 已安装目录，用于让桥接层拿到合法 id 并让每个请求落到明确的未实现错误，与本次移除无关。
- 模型覆盖不受影响：7 个模型分别可在 `openrouter`（全部）与 `together`（`openai/gpt-oss-120b`、`llama-3.3-70b-versatile`）上选择。
- 未触及 agent loop、模型可见工具、Session 事件或持久化格式；`deepseek-official` 与 `deepseek-account` 原生路由不受影响。

## 4. 复查记录

- 覆盖核对：`groq` 的 7 个模型逐一在其他已提供路由上确认——`llama-3.1-8b-instant`、`llama-3.3-70b-versatile`、`openai/gpt-oss-120b`、`openai/gpt-oss-20b`、`openai/gpt-oss-safeguard-20b`、`qwen/qwen3.6-27b`、`qwen/qwen3.8-27b` 均出现在 `openrouter`；`openai/gpt-oss-120b` 与 Llama 3.3 70B 另见 `together`（后者在 `together` 上的 id 为 `meta-llama/Llama-3.3-70B-Instruct-Turbo`）。因此文档写「移除托管面而非模型覆盖」。
- 连带修正：`cerebras` 的说明原写「`gpt-oss-120b` 在四条路由、Qwen3.8 27B 在两条」，与实测（`openrouter`、`together`；`openrouter`）不一致，且移除 `groq` 后必须重算；已同步 `catalog.ts` 注释、包 README（中英）与用户指南（中英）。
- 升级指南词数在加词后一度超出上限，通过合并 `cerebras` 与 `groq` 的覆盖句、精简迁移步骤与结尾句压到 498 词。
- 未改动 `provider-data.generated.ts` 与 `packages/experimental/webworker-runtime` 的 stub 列表：两者描述已安装目录而非可售路由，`verify-provider-data` 要求保留全部 42 个 id。
- Web golden 三份文件均为 17 项且不含 `groq`，`models-settings.e2e.ts` 下界断言为 17。
- 2026-11-17 二次复查（逐项核对修复）：用构建产物 probe 确认 `catalogProviderIds()` 为 17 条、`catalogProvider('groq')` 为 `undefined`、`catalogModels('groq')` 为空、模型合计 652，且 `lib/types/catalog.js` 的 withheld 集合含 `groq`，说明构建未落后于源码；`verify-provider-data` 与 `gen-config-catalog --check` 均通过。
- 二次复查修正 3 处与实际不符的描述：根 README 原写「7 个模型在 `openrouter` 与 `together` 上都能取到」，实际仅 `gpt-oss-120b` 与 Llama 3.3 70B 在 `together` 上；用户指南（中英）把 `llama-3.3-70b-versatile` 写成 `together` 上的 id，实际为 `meta-llama/Llama-3.3-70B-Instruct-Turbo`，且两个 Llama 在 `openrouter` 上为 `meta-llama/` 前缀；`00009` 的「全部以同 id 提供」与本节旧句自相矛盾。修正后重录 `providers.i18n.yaml` 并重跑文档门禁。
- 二次复查用脚本把 4 份文档清单（升级指南中英、用户指南、包 README、根 README）与 `WITHHELD_PROVIDERS` 逐项比对，均为 24 条、无缺失无多余。

## 5. 已知限制与恢复

- 本次只屏蔽可售路由，不删除 pi-ai 包内 Groq 的实现与目录元数据；手工声明同名路由仍会被 `resolveProfiles()` 拒绝。
- 恢复时删除 `WITHHELD_PROVIDERS` 中的 `groq`，把可售路由与模型计数改回 18 / 659，并同步撤销第 1 节列出的 golden、断言与文档改动；升级指南词数（498，上限 500）需重新核对。
- 运行中的 Web 宿主仍是改动前启动的进程，重启 `pnpm dsh web` 后设置页才会显示 17 项且不含 `groq`。
