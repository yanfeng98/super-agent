# 00065 — 主会话完成合并与收尾

- **日期**：2026-11-19
- **背景**：用户希望链路是「人在主会话派活 → worker 干活 → 主会话问一句能不能合 → 人说合 → 就合完」。上一版已经能从主会话合并，但目标分支一前进就要人去面板点 Rebase、点 Run check、点 Clean up，等于把收尾推回面板。面板应只负责记录和评审。
- **范围**：`src/app/review.ts`、`src/app/runtime.ts`、`src/app/tools/main.ts`、`prompts/orchestrator.md`、`tests/`、`docs/`、`NATIVE.md`。

## 1. 合并自带 rebase

`Runtime.mergeTicket` 在进门禁之前先看工单分支是否已包含仓库当前提交（`targetContained`）。不包含说明目标分支前进过，于是直接调用 `rebaseTicket`：改写工单分支、把 `execution.base` 移到目标分支当前提交、重新采集 review、清掉旧的 check 和评审决定。合并成功后返回值多一个 `rebased: true`，主会话据此告诉人"先 rebase 再合了"。

`mergeWorkspace` 里原来的祖先判断抽成 `contains`，`targetContained` 复用它；合并本身仍然要求祖先关系，冲突依旧不会出现在合并阶段。

## 2. 合并自带 check

门禁里 check 没过时（刚 rebase 会清、或工单结束早于命令配置），`mergeTicket` 不再抛"去工单页跑一下"，而是当场跑一次 `checkTicket`：通过就继续合并，失败就把退出码和输出末尾 800 字符带回给主会话，工单仍是已结束状态，人可以让人或 worker 修。这样一次"合并"指令就覆盖了面板上的 Merge + Run check 两步。

## 3. 冲突怎么说

`rebaseWorkspace` 冲突时在 `--abort` 之前先读 `git diff --name-only --diff-filter=U`，把仍在冲突的文件名带进错误：`Rebasing onto main conflicts in a.ts, b.ts; the Ticket branch keeps its commits`。abort 之后工作区和工单分支都保持原样，不会停在 rebase 中间态。

提示词没有加长（`tests/cards.spec.ts` 要求主线指令保持在 1400 字符内，且工具语义本来就该写在工具描述里）：`orchestrator_ticket_merge` 的描述写明"目标前进会 rebase、check 没过会跑、只合本地不 push"，`orchestrator_ticket_rebase` 的描述写明"冲突会 abort 并保留提交，之后用 `orchestrator_answer` 把活送回 worker"。

## 4. 两个新工具

- `orchestrator_ticket_rebase`：显式 rebase，行为同面板 Rebase。
- `orchestrator_ticket_cleanup`：合并后删 worktree 和已合并分支，行为同面板 Clean up worktree；不自动执行，因为清理后工单页的 View diff 就读不到了。

合并工具的描述也更新为"目标前进会 rebase、check 没过会跑、只合本地不 push"。为容纳两个工具和一句提示词，orchestrator 的模型面预算从 59,800 调整到 61,500（三个描述加提示词约 1,100 字符）。

## 5. 范围与已知限制

- 合并仍是人的明确请求触发，主会话不会自己合。
- `executor.requireReview` 打开时不自动 rebase：rebase 会清掉批准，自动做只会把工单推进死路，所以这种情况在改动任何东西之前就拒绝，提示去工单页 rebase 后重新批准。批准属于评审，仍由人在面板做，这是有意的分工。
- 手动或 worker 自己做的 rebase 仍不会刷新 `execution.base`，review/diff 会把上游提交算进来；这次没动，留给下一步。
- 合并不做 push，也不做合并队列：多张工单依次合并时，后一张会自动 rebase，但仍是串行完成。
