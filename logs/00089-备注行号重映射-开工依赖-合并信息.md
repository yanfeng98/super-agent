# 00089 — 备注行号重映射、开工依赖与合并信息

- **日期**：2026-11-20
- **背景**：上一轮列出的三个问题：评审备注只判断“过时”而不移动行号，插入/删除后可能标为未过时却画在错误的行；`blockedBy` 只挡合并、不挡开工，依赖工单仍从旧目标起工作树；squash/merge commit 只用分支名，工单标题和报告摘要没进历史。
- **范围**：`src/core/model.ts`、`src/core/tickets.ts`、`src/core/engine.ts`、`src/executor/dsh.ts`、`src/app/runtime.ts`、`src/app/review.ts`、`src/app/tools/main.ts`、`src/app/http.ts`、`src/app/api.ts`、`src/app/views/tickets.ts`、`src/client/ticket.tsx`、`src/client/locales.ts`、`tests/`、`docs/001`–`007`、`README.md`、`NATIVE.md`、`logs/`。

## 1. 备注行号随代码移动

- `staleNoteIds` 换成 `remapNoteAnchors`：按 `git diff --unified=0 -M <note.commit>..<head>` 的 hunk 解析旧行/新行区间。
  - 备注在 hunk 之后：行号加上 `newCount - oldCount`；
  - hunk 本身覆盖备注的行/区间：替换或删除，标 `stale`；
  - 纯插入不改变已有行，只移动后面的行号；
  - 新增/删除/重命名/二进制文件按整文件处理；
  - 文件级备注只在有内容行变化时过时，纯 mode 变化不算。
- 重映射成功后备注的 `line`/`endLine` 更新到当前 head，`commit` 也更新到该 head，`checkedHead` 记下检查点；下次移动以新 head 为基准。过时的备注保留原行号并标 `stale`，不再参与行内渲染。
- 面板 `DiffPatch` 只把未过时的备注画在行下；过时备注留在备注列表里，显示 **Changes moved**，避免把评论锚到错误的代码行。
- `noteOutdated` 仍是统一判断：`stale` → 过时；已按当前 head 检查 → 不过时；旧记录没有检查点 → 回退到整头比较。

## 2. 依赖可以挡开工

- `Ticket.startAfter`：必须等这些工单合并后，本工单的第一个 Assignment 才启动；它是 `blockedBy` 的子集。
- `Tickets.block`/`Engine.blockTicket`/`Runtime.blockTicket` 增加 `start`：
  - `blocked: true, start: true`：同时记入 `blockedBy` 和 `startAfter`；
  - `blocked: true, start: false`：只挡合并，并清掉该依赖的开工限制；
  - `blocked: false`：两者一起清掉。
- `DshExecutor.start` 在入队前检查：工单还没有任何 `startedAt` 的 Assignment，且 `startAfter` 里有未合并的工单时，不排 launch；Assignment 保持 pending，工单显示为排队。
- `Runtime.startWaiting` 在两种时机启动等待中的工单：一次合并成功之后，以及记录/清除依赖之后（依赖的工单已经合并时立即开工）。它只启动“没有 startedAt、最新 Assignment 仍 pending、所有 startAfter 都已合并”的工单。
- 面板：阻塞项显示 **Wait before starting** 标签；添加阻塞项的输入旁多一个同名复选框；`POST tickets/<id>/blockers` 接受 `{ start }`，返回的 `blocked_by` 每项带 `start`。
- chat：`orchestrator_ticket_dependency` 增加 `start` 参数，描述说明它同时挡开工；`blocked_by` 返回也带 `start`。
- 只挡第一个 Assignment：已经开工的工单重试/恢复不会被再次挡住。

## 3. 合并提交信息

- `mergeWorkspace` 增加可选 `message`：
  - `squash`：`git commit -m <message>`，没有 message 时仍是 `Squash merge <branch>`；
  - `merge`：`git merge --no-ff -m <message>`，没有 message 时用 `--no-edit`；
  - `ff` 不产生合并提交，保留 worker 自己的提交。
- `Runtime.mergeOnce` 组合信息：工单标题、worker 最近一次报告摘要、`Ticket T-000N`（没有编号时用 id），最多 4000 字符；squash/merge 提交因此能独立读懂，和 GitHub 的 PR 标题/正文对应。
- 合并记录、归档和面板历史不变；提交本身带信息。

## 7. 仍然存在的差距

- 真正的并行堆叠：B 从 A 的未合并分支起需要 prepare 命令使用 `DSH_SUPERAGENT_BASE`，并处理 A 被丢弃/回退的情况；这轮只做了“等 A 合并后开工”。
- 合并目标只能是当前检出分支，不能像 GitHub 选 base。
- 队列串行，慢检查会阻塞后面的条目；目标检查失败只暂停并通知，不自动回退。
- 评审没有 suggested change；已查看标记只存浏览器。
- 单人部署，没有按人分配评审人、多人批准或 CODEOWNERS。
