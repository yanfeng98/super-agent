# 00060 — 请求编辑、备注回复、合并策略与通知收件箱

- **日期**：2026-11-18
- **背景**：00059 之后，继续处理上一轮列出的剩余项：请求正文不可编辑、评审备注没有逐条回复、合并只有快进、通知只在浏览器打开时可见，以及缺少合并策略选择。
- **范围**：`src/core`、`src/app`、`src/client`、`src/sources/local.ts`、`docs/`、`tests/`。

## 1. 请求正文编辑

- `Ticket.request` 保存最近一次替换的请求正文；起始 Trigger 保持 Source 交付的原文不变，工作线程已经读过的内容不会被追改。
- `Tickets.editRequest`、`Engine.editRequest`、`Runtime.editRequest`、`POST tickets/:id/request` 接通；空白正文拒绝。
- 工单页 **Request** 区块新增 **Edit request**，显示编辑时间；搜索匹配替换后的正文，本地归档追加 **Request** 段，启动对账补写。
- `emptyRequest` 错误与中英文案已补。

## 2. 评审备注逐条回复

- `TicketNote.replies` 保存回复；`Tickets.replyToNote`、`Engine.replyToNote`、`Runtime.replyToNote`、`POST tickets/:id/notes/:noteId/replies` 接通。
- 面板每条备注显示讨论并按条回复；空白回复拒绝（`emptyNoteReply`）。
- 回复仅属于工单元数据，不改变备注的解决状态或合并门。

## 3. 合并策略

- `mergeWorkspace` 接受 `ff`、`squash`、`merge` 三种策略：快进、压缩为一个提交、保留合并提交；三者都先要求 Ticket 分支包含仓库当前提交，因此不会留下冲突状态。
- `Runtime.mergeTicket(id, strategy)`、`POST tickets/:id/merge?strategy=…` 与工单页合并方式选择器接通；`ticket.merged.strategy` 与归档 **Merged** 段记录非默认策略。
- 绑定 PR 的 CI 失败时，面板合并读取其 Thread 上的 CI 事实并拒绝；新测试覆盖该门。
- 新测试覆盖 squash 的单父提交与 merge 的双父提交，以及 HTTP 参数校验。

## 4. 面板通知收件箱

- `src/app/notifications.ts` 持久化工单“等待回复”和“结束”通知，列表按时间倒序，支持未读数、单条已读和全部已读。
- `Runtime` 在 `ticket.attention` / `ticket.ended` 事件中写入通知；新增 `GET notifications`、`POST notifications/:id/read`、`POST notifications/read-all`。
- 面板页头新增通知按钮与未读数，弹窗列出通知、跳转到对应工单并标记已读，支持全部已读。
- `tests/notifications.spec.ts`、面板测试与 HTTP 测试覆盖；`docs/007` 的模块表与测试表已补。

## 7. 范围说明

- GitHub 历史 Issue/PR 不导入：`observeIssues` 明确从开关启用时开始读，不镜像已有 backlog；需要从 GitHub 开始时继续用 GitHub，需要本地工单时从面板新建。
- GitHub PR 的失败 CI 由面板合并门拒绝（读取绑定 Thread 的 CI 事实）；auto-merge 仍由 worker 按 delivery requirements 和 GitHub 分支保护处理，面板合并只作用于本地工作树。
- revert 与冲突解决沿用 git：rebase 冲突直接 abort 并保留原提交，操作者在工作树中解决；面板不提供冲突编辑器。
- 批量关闭由批量停止覆盖；里程碑、优先级、截止日期、多用户、邮件摘要等仍为既定非目标。
