# 00066 — 收敛主会话的工具面

- **日期**：2026-11-19
- **背景**：上一版给主会话加了 `orchestrator_ticket_rebase` 和 `orchestrator_ticket_cleanup`。对照 `docs/000` 的"少概念、少设置、按注意力成本取舍"和主会话"评估与路由"的定位，这两个工具把主会话往"git 运维"推了一步，模型面也从 14 个工具涨到 19 个、预算从 59,800 抬到 61,500。
- **决策**：主会话只代替人执行**建单、回答、合并**三类 Ticket 动作；批准、改名、标签、单独的 rebase、清理、丢弃留在面板。合并所需的两步（目标前进时 rebase、check 没过时补跑）已经由 `mergeTicket` 内部完成，单独的 rebase 工具没有独立场景。
- **范围**：`src/app/tools/main.ts`、`src/app/runtime.ts`、`tests/`、`docs/`、`NATIVE.md`。

## 1. 删除两个工具

- 删 `orchestrator_ticket_rebase`：合并自带 rebase，冲突时本来就要把活送回 worker，单独暴露只会多一个模型要选的动作。
- 删 `orchestrator_ticket_cleanup`：改用 `orchestrator_ticket_merge` 的可选参数 `cleanup` 承载；默认不清理，因为清理后工单页的 View diff 就读不到了。

`MainToolsHost` 和 `toolHost` 里对应的两个方法一起删掉，面板的 `POST tickets/:id/rebase` 和 `/cleanup` 不受影响，仍然走 `Runtime`。

## 2. 合并带清理

`Runtime.mergeTicket(id, strategy, { cleanup })`：合并记录完成后再删 worktree 和分支，返回 `cleaned: true`。清理失败时不推翻已完成的合并，报 `Merged agent/x into main, but removing its worktree failed: …`，让主会话把"已合并、清理失败"原样转述给人。

## 3. 边界写进文档

- `002`：明确主会话只代替人执行建单、回答、合并（可带 `cleanup`）；批准、改名、标签、单独 rebase、丢弃留在面板。
- `003`：主会话段落和 Clean up worktree 段落改为 `cleanup` 参数的说明。
- `006`：同一处表述同步，并点明哪些动作留在工单页。
- `007`：工具表从 19 个改为 17 个（16 个应用工具 + `orchestrator_read`），合并返回值加上 `cleaned?`；测试表补 cleanup。
- `NATIVE.md`：本地改动清单同步。

## 4. 预算

模型面从 61,500 降到 **60,300**；实测 59,966（42,537 字符提示词 + 17,429 字符工具），比加工具前只多约 170 字符，来自合并描述里新增的 rebase/check/cleanup 说明。

## 5. 验证

- 包测试：67 个文件、**1308** 个用例全部通过（清除宿主继承的 `GIT_CONFIG_GLOBAL` 后）。
- `pnpm typecheck`：通过。
- `tests/merge.spec.ts`：新增 cleanup 成功、cleanup 失败不推翻合并两个用例。
- `tests/chat-tools.spec.ts`：合并工具带 `cleanup` 时透传 `{ cleanup: true }`，默认 `{ cleanup: false }`。
- `tests/model-surface.spec.ts`：预算降到 60,300 后通过。
- 仓库 `test:docs`：21/21；`lint` 与 `build` 见提交前的门禁输出。
- 预推送 typecheck：5/5。

## 6. 范围

- 面板仍是记录与评审的地方：批准、备注、改名、标签、单独 rebase、丢弃、清理都在面板。
- 主会话不做技术决定，也不新增 git 语义；`cleanup` 只是把面板已有的同一个动作并进合并请求。
- 冲突仍由 worker 解决（`orchestrator_answer` 转达人的话），主会话不手动解冲突。
