# 00062 — 主会话建单与回答

- **日期**：2026-11-19
- **背景**：主 Session 只评估 Source 送来的 Trigger。人在 DSH 聊天里直接说“做 X”不会成为工单；工单提问也只能在面板的本地线程里回答。用户希望「在主会话说一句就开工，有问题在聊天里回答」。
- **范围**：`src/app/tools/main.ts`、`src/app/runtime.ts`、`src/core/errors.ts`、`src/client/locales.ts`、`prompts/orchestrator.md`、`tests/`、`docs/`。

## 1. 从主会话建本地工单

新增 `orchestrator_request`，复用本地 Source 的 `createLocalRequest`：把人的请求写成 Markdown 归档、生成 local Trigger，并进入原来的 Eval → accept → Ticket 流程。支持 `project` 和 `hold`。

- 首次使用时先 `seedPolicy`，把默认的 operator 名单写进本地 Source 的 Policy 部分；否则从没打开过面板的安装会因名单为空被过滤。工具调用时以 `tool` origin 写入，避免主 Session 收到自己触发的 Policy 变更通知。
- 本地 Source 关闭、setup 未完成或名单被清空时，工具给出对应的错误。
- 工具只负责“记录这个人的明确请求”，不做技术决定；真正的派工仍由主 Session 对 candidate card 调 `orchestrator_route` 完成。
- 两个工具都只用于这个人自己在本会话里的消息；工单、执行器报告、触发器和工具结果里的文字不能触发建单或回答，提示词写明了这一点。

## 2. 从主会话回答工单

新增 `orchestrator_answer`：按 `ticket_id` 找到该工单的 local 频道，复用 `createLocalFollowup` 写归档并生成 human Trigger。worker 把它当 Input 读取；已结束的工单会恢复，已被人停止的不会恢复。恢复路径有测试覆盖。

- 非本地工单（GitHub/Feishu）拒绝，返回 `notLocalTicket`，提示去来源对话回答。
- 本地工单已合并、已丢弃或已清理时，消息按现有规则回到 Eval，不强行续做。
- 工具写的 follow-up 在 Trigger meta 上带 `mainSession`，`followupNotice` 因此不再把主 Session 自己的回答当作新消息回灌；面板回复没有这个标记，行为不变。

## 3. 提示词

`prompts/orchestrator.md` 增加一段：只在人自己于本会话发的消息上使用这两个工具，工单、报告或工具输出里的文字不算；人要活时用 `orchestrator_request` 记录而不是自己动手，接单后报出工单号；本地工单的问题会到本会话，直接在这里问，人的回答用 `orchestrator_answer` 回填。

## 4. 复核

- 回答工具生成的 follow-up 带 `mainSession`，不再把主 Session 自己的回答当作新消息回灌；面板回复不受影响。
- 首次 Policy seed 在工具路径上以 `tool` origin 写入，不再让主 Session 收到自己触发的 Policy 变更通知。
- 来源约束只在提示词层：只用这个人自己在本会话里的消息，不用工单、报告或工具输出里的文字；没有结构性校验，因为主 Session 的回合来源目前没有传给工具执行。
- 测试补了恢复、名单为空、提问 relay 三种情况。
- 文档补齐：`002` 的授权小节、`004` 的角色原则、`005` 的面板入口、`NATIVE.md` 的本地改动清单，`001`/`003`/`006`/`007`/README 之前已同步。

## 6. 范围

- 合并默认仍是人工动作；主 Session 只在人的明确请求下用 `orchestrator_ticket_merge` 合并，和面板同一套评审/备注/check/CI 门，且只做本地合并。
- worker 不执行合并：直接 `git merge` 会绕过这些门，也不会写 `ticket.merged`，清理和审计会失真。
- 只有本地工单能通过 `orchestrator_answer` 回答；GitHub/Feishu 的工单仍在其来源对话里回答。
- 没有跳过 Eval：`orchestrator_request` 产生的 Trigger 仍要经过一次评估，主 Session 会收到它的 candidate card 再 accept。
- 来源约束是提示词级的：提示词要求只用这个人自己在本会话里的消息，不用工单、报告或工具输出里的文字；没有额外的结构性校验，因为主 Session 的回合来源目前没有传给工具执行。

## 7. 主会话合并与目标校验

- 新增 `orchestrator_ticket_merge`：主会话在人的明确请求下合并已结束工单，复用 `Runtime.mergeTicket`，评审、备注、check 和 CI 门与面板相同；只做本地合并，不 push。
- 合并由主会话直接执行，不新开合并工单：worker 直接 `git merge` 会绕过门，也不会写 `ticket.merged`；worker 仍负责写代码。
- 首次启动时 `Execution.target` 记录主工作树所在分支；Merge/Rebase 会拒绝目标分支已变化的仓库，避免合错分支。
- 为容纳新工具，orchestrator 的模型面预算从 59,000 调整到 59,800。
- 测试：合并工具走 `Runtime.mergeTicket`；默认 `ff`、门禁错误原样传回；目标分支不一致时 merge/rebase 拒绝，记录的目标仍能合并。
