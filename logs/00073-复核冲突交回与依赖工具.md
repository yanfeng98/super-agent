# 00073 — 复核：冲突交回、依赖工具与 push

- **日期**：2026-11-19
- **背景**：00072 落地后按要求自查。逐条对照代码、测试和文档，发现四处不够正确或不一致的地方，都修掉了；另外补了一个真实 git 的 push 测试。
- **范围**：`src/app/runtime.ts`、`src/app/tools/main.ts`、`src/app/http.ts`、`src/app/api.ts`、`src/core/tickets.ts`、`tests/merge.spec.ts`、`tests/chat-tools.spec.ts`、`tests/review.spec.ts`、`tests/http.spec.ts`、`docs/003`、`docs/006`、`docs/007`。

## 1. 依赖工具的编号不对称

`blocker_id` 走 `ticketReference`，接受 `T-0003`；`ticket_id` 没有解析，只认内部 id。工具描述里却用 `T-0003` 举例，模型很可能两边都传编号，然后拿到 `Unknown ticket`；即使 `blocker_id` 用编号成功，工具返回的卡片也会因为查不到而消失。

修法：

- `Runtime.blockTicket` 同时解析 `id` 和 `reference`，两者都接受内部 id 或 `T-0001` 形式；
- 返回值加上 `ticket_id`（解析后的 id），工具据此取卡片；
- `HttpHost`、`api.ts`、`tests/http.spec.ts` 同步这个字段；
- docs/006 的 blockers 一行写清：路径里的 `<id>` 是工单 id，body 里的 `ticket` 可以给编号。

## 2. 冲突说明的措辞把 rebase 说成 merge

原注释写 “The merge into main conflicts in a.txt”，但实际没发生合并，是 rebase 冲突。改成：

> Rebasing the ticket branch onto main to merge it conflicts in a.txt, b.txt; the branch keeps its commits. In your worktree, run "git rebase main", …; report ready again once the branch is rebased.

同时把这条 Input 从 `undelivered` 末尾改到队首：它是 worker 重新开工的原因，应该先读；`wake` 的 `resumed` 标记也是同样的处理。

## 3. push 失败后没有可行的下一步

文档只说“报告 `pushError` 不回滚合并”。但 `mergeTicket` 对已合并工单直接拒绝，工具层面就没有再推一次的入口。

这次不改协议，只把恢复路径写实：docs/003 明确“之后在仓库里再 `git push` 即可完成”（主会话有 shell，也可以由它执行）。同时让 push 的风险面可验证——新增真实 git 的测试：本地裸仓库做 origin，推送后比对两边的 `HEAD`；另有一个没有 upstream 的仓库，确认报错且不动分支。

## 4. 测试没有证明 worker 真的收到冲突

原来的断言只看 `ticket.inputs`。现在补：

- `h.deliveries` 里确实出现那段冲突说明（真实经过 Executor 投递，不是只写进记录）；
- 工单多了一个 Assignment（`assignments` 长度为 2）。

依赖工具那条测试也加上了编号路径：先用内部 id 记录，再用 `T-0001` 记录一次，确认解析成功且卡片返回正确的 `ticket_id`。`review.spec` 的冲突用例改为断言 `RebaseConflictError` 的 `target` 和 `files`，把交回逻辑依赖的那份契约钉住。
