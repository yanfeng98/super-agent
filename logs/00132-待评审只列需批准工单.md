# 00132 — 待评审只列真正需要批准的工单

- **日期**：2026-11-25
- **背景**：`ticketList` 的 `review` 筛选把一切未合并、未丢弃、未批准的已结束工单都算作待评审。用户放弃的工单、已完成但没人要求合并的工单因此混进待评审，与「已完成」「已放弃」的语义冲突。
- **需求补充**：已放弃的工单不进待评审；已完成的工单若没合并显示为「已完成但未合并」，仍不算待评审，除非确实有改动需要批准且用户要求合并（登记了待合并请求或进了合并队列）。

## 1. 变更

| 位置 | 变更 |
|---|---|
| `src/app/views/records.ts` | 新增 `needsReview`：仅当工单已结束、有捕获到的改动、未批准、未合并/未回退/未丢弃/未清理，且存在待合并请求（standing 或队列）时进入待评审 |
| `src/app/views/tickets.ts` | `ticketList` 的 `review` 分支改用 `needsReview`，并传入合并队列状态 |
| `src/client/locales.ts` | 新增 `outcome.completedUnmerged`；改写 `reviewFilterHint` 说明新口径 |
| `src/client/marks.ts` | 已结束且未合并的 completed 工单显示「已完成但未合并」 |
| `docs/005-panel.md` | 更新待评审筛选和已完成标记的文档 |
| 测试 | `views.spec.ts` 覆盖放弃/完成无改动/无合并请求/合并/回退/线程已合并/队列请求；`marks.spec.ts`、`panel-execution.spec.tsx` 更新标记文案 |

## 2. 原因与判断

- 待评审不是「所有未合并的结束工单」，而是「有人要求落地、且还等人批准改动」的工作清单。用户放弃、无需处理、关闭未合并、已完成但不请求合并都没有待批准的改动，故不进入。
- 已合并或已回退的工作已经落地或被撤销，同样不再需要批准。
- 完成但未合并的工单本身仍保留在「已结束」列表里，标记改为「已完成但未合并」，避免把「完成」误读为「等待评审」。
